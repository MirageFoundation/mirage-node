# Mirage v1.26.0 Release Notes

### Why This Release Exists

On May 25, 2026 the production validator at mirage.talk forked off the network at block 4,854,225 and, after the divergence watchdog recovered it via state-sync, panicked on the next block with `panic: invalid denom:` from the mint module. Both failures had the same root cause hiding inside the chain's local IAVL patch: a missing entry in the secondary fast-node read index at the latest version was being treated as proof that the key did not exist in IAVL at all. The fast-node index is a cache. The canonical IAVL tree, rooted at the version's app hash, is the source of truth. Treating an advisory cache as authoritative produced silent, deterministic divergence the moment two nodes happened to have differently populated indices — which is exactly what state-sync produces. v1.26.0 fixes this everywhere it lives, on every read path, with no on-chain state change, and ships it as a coordinated upgrade because the IAVL read contract change is itself state-machine breaking.

### What Changed In The IAVL Patch

Every read path under blockchain/patches/iavl now treats a fast-node miss as a hint, never as proof of absence. ImmutableTree.Get and MutableTree.GetVersioned no longer short-circuit to nil when the index reports no entry at the latest version — they fall through to a canonical IAVL traversal of the same key. ImmutableTree.Iterator, ImmutableTree.Iterate, MutableTree.Iterator, and MutableTree.Iterate no longer return a fast-node-only iterator. They always walk the canonical tree, which means every range scan is guaranteed to surface every key that the verified app hash certifies is present, regardless of the local index's state. Fast-node hits for point reads at the requested version are still served from the index unchanged, so the steady-state point-read path is no slower. Range iteration is now unconditionally canonical and may be slower on very large scans, but the trade-off is intentional: a complete canonical scan is safe, while a fast scan that silently omits keys is a fork.

### Why This Has To Be A Coordinated Upgrade

The handler in app/upgrades.go is intentionally a no-op for on-chain state. There are no new chain parameters, no new store keys, no module migrations, and no deploy-side migration. What is breaking is the local read contract: a pre-v1.26.0 node observing an empty fast-node entry returns nil; a v1.26.0 node returns the canonical value. Two binaries running side-by-side against the same canonical state will compute different app hashes the moment one of them encounters a fast-node miss. Activating the fix at a planned upgrade height across the validator set is therefore mandatory even though, on paper, nothing about the chain state is changing. After v1.26.0 is live everywhere past the upgrade height, state-sync recovery is safe again on this chain — until then, watchdog recovery should continue to prefer peer-pull, which copies the source's already-populated fast-node index and is not exposed to this bug class.

### Regression Coverage

A new test file at blockchain/patches/iavl/fastnode_import_test.go reproduces the production state-sync failure shape deterministically: a destination tree's canonical IAVL is fully populated via Export and Import at version V, the fast-storage version is marked current at V before the import so the destination believes its index is authoritative, and then every read path is asserted to return the canonical value for every imported key. The test covers point reads, historical reads, full iterators, range iterators, callback iteration, and the empty-tree iterator edge case. The keys are intentionally representative of the production failure — staking parameters that produced the BondDenom panic, the recent-block-hashes structure that ran during the original divergence, and the proof-of-work counter at the divergence height — but the invariant being checked is not Cosmos-SDK-specific. It is the IAVL-level promise that all read paths agree with the canonical tree when the secondary index is incomplete, which is exactly the promise that was silently being broken in production.

### How CI Catches A Regression

Because patches/iavl is its own Go module, plain go test on the blockchain workspace skips it. The Makefile now wires test-iavl into both the test and test-fast targets, so the regression suite runs on every CI gate, every developer's pre-commit run, and every release build. The new test target is an explicit dependency of test-fast, not a side door — if the fast-node correctness contract is ever broken again by a future patch refresh, the build fails before any binary ships.

### Operator Notes

There is nothing to do post-upgrade beyond the usual verify_upgrade.py run, which has been rewritten to v1.26.0-only checks: that the handler ran, that the post-migration params validation logged successfully (the v1.25.0 fail-fast contract is still in force and will catch any params corruption introduced by the upgrade), that the indexer is producing fresh blocks, and that the frontend version cross-checks. Once the chain has crossed the upgrade height and validators have all reported clean, the divergence watchdog's RECOVERY_MODE can stay on peer-pull — there is no urgency to switch back to state-sync, but the option is now safe again. The full incident, root cause analysis, every read path that was patched, and the proven-versus-evidence-consistent split for the two production failures are documented at docs/troubleshooting/state-sync-bonddenom-panic.md.
