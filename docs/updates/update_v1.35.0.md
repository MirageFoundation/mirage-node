# Mirage v1.35.0 Release Notes

### Deleting your account can no longer take the platform's memory offline

Mirage keeps two things: the chain, which is the record of what happened, and an index built from it, which is what actually answers your feed, your profile, your balance and your follow lists. This release closes a way for one ordinary account to stop that index permanently. Deleting an account removes its profile from the chain, and until now a request for a profile that no longer existed came back as a plain error rather than as "that account is gone". The indexer read the error the only way it could — as a sign that something was broken — refused to finish the block it was working on, and started the same block again. Forever. The chain would keep producing blocks while every reader on that node saw a platform frozen at one moment in time, and rebuilding from scratch would stop at the same block. It cost one transaction and no special access.

### Telling "gone" apart from "broken"

The fix is a distinction that was missing. A profile that isn't there now answers with a specific "not found" instead of a generic failure, and the indexer treats that as the ordinary situation it is: it notes the absence, skips that one refresh, and carries on with the block. This matters more than it sounds, because the honest version of this fix is not "ignore errors". Every other kind of failure — an unreachable node, a broken connection, a database that won't answer — still stops the block exactly as before. That is deliberate: if we had made every failure survivable, a node having a bad day would quietly record "this user follows nobody" and wipe live accounts' lists instead of complaining. Only genuine absence is survivable. The same reasoning was applied to a second version of the same trap: an indexer that meets a kind of message a newer chain introduced now logs it and moves on rather than halting. The tradeoff there is stated plainly — that height ends up indexed incompletely until the operator upgrades and replays it, which is a far better outcome than the whole platform stopping.

### One referral, one reward

While reviewing the reward paths we found that the invite referral bonus could be paid more than once to the same pair of people. The record of who invited whom is permanent by design, but nothing checked that the payout only happened at registration, so a later username change could satisfy the same conditions again and mint another bonus on both sides. We are not going to be coy about this: it happened. One account was paid the referee bonus twice, three days apart in April, and both payments were claimed — roughly twenty thousand MIRAGE issued that should not have been. The payout is now tied to the moment an account first takes a username, and only when that transaction actually succeeded, which makes it unrepeatable for the life of the account. The tokens already issued have not been reversed; undoing them would be a separate decision, and we would rather record the number honestly than quietly round it away.

### A node joining the network cannot be talked into running commands

When a new node joins Mirage it asks existing nodes where the chain is, and it uses the answer to configure itself. That answer was being handed to the system shell as a script rather than read as data, which means a peer that replied with something other than a block reference could have run commands on the joining machine, as the administrator, during the one window when that machine is being handed its keys. Nothing in the answer is executed now. Each expected setting is read, checked for the shape it must have — a block reference has to be exactly a block reference — and anything unexpected stops the join with an error instead of being obeyed. The check is enforced at both ends, so a hostile answer is refused before it reaches the shell at all.

### A restored server exposes exactly what a normal one does

Rebuilding a node from a backup is supposed to produce the same server you had before. It did not quite: the restore path opened two additional network doors that a normal deployment keeps shut, exposing the chain's raw query interfaces directly to the internet instead of keeping them behind the front door where they belong. Anyone reading our deployment script — the obvious place to check what a Mirage node exposes — would have seen the correct, smaller list. The two paths now share a single definition, so they cannot disagree again, and the build fails if anyone spells the list out separately in either place. We checked every server in the fleet: none was running in the exposed state.

### Tested, and coordinated across the fleet

Each fix in this release ships with a test that fails when the fix is removed, and we verified that by removing them: the indexer now has offline coverage proving an absent profile is skipped without touching the database while a node outage still stops the block, the join path is tested against an answer containing a shell command, the two port lists are compared against each other at build time, and the referral payout is checked to be reachable only from registration. The post-deployment verification script asks the running node for a profile nobody owns and requires the correct "not found" answer, so a server that missed this update is visible rather than assumed. This is a query-side change with no effect on how transactions are processed or how state is written, so unlike the last release it is not consensus-breaking and mixed versions will not diverge. It still goes out as a coordinated upgrade at a single height, for a simple reason: a validator left behind is a validator whose own index can still be stopped by anyone who asks.
