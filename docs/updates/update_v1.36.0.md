# Mirage v1.36.0 Release Notes

### Two timers that were already counting down

Mirage keeps the chain, which is the record of what happened, and an index built from it, which is what actually answers your feed, your profile and your balances. This release defuses two ways that index could have stopped permanently — not through an attack, but through the platform simply being used. The first was hiding in how the indexer read governance activity: it guessed that the labels attached to each event were encoded, and tried to decode them. Most of the time the guess was harmless. But roughly one proposal number in nine, once numbers reach four digits, happens to look exactly like encoded data and quietly turns into nonsense. The moment that happened, the block would fail, roll back, and be retried forever, on every node at once, with rebuilding from scratch stopping at the very same block. We measured how much time was left: the network is at proposal 108, and the first number that breaks is 1400.

### The second one needed a single ordinary decision

The other timer was simpler and closer. The chain treats anyone at level 100 or above as an administrator, an open-ended range by design. The indexer had been written against a fixed list of levels and knew about exactly 100. Any other administrator level — 101, 150, anything — was a value it had no answer for. It would not have failed at the moment the level was granted; it would have failed later, on the first ordinary post or vote by that account, and then kept failing on that block forever. Nothing about this required bad intent. A routine governance decision to give someone a slightly different administrator level would have been enough, and the damage would have looked like an unexplained outage rather than a consequence of the vote. The indexer now derives administrator status the same way the chain does, from the range rather than a list, so the two can no longer disagree.

### Deleting a post no longer leaves the credit behind

Influence on Mirage is earned per topic: participate in a topic and your votes there carry more weight. That credit was being granted when a post was made and never taken back when the post was deleted, which meant the same effort could be banked over and over — post, self-vote, delete, repeat — until the account had accumulated enough standing in a topic to downvote with full force without ever leaving anything visible behind. It was cheap, it left no trace on the site, and it worked. Deleting a post now withdraws the standing it granted its author, and a repair pass rebuilds the affected histories so that credit banked before this release does not survive it. We want to be straightforward about one deliberate limit: other people who voted on a post keep what they earned when it is deleted. Taking theirs away too would have closed the same hole, but it would have handed authors a new lever — delete your own popular post to strip standing from someone you dislike. We would rather leave a smaller gap than open a way to harm other users.

### An index that refuses to erase itself

While reviewing how the indexer synchronises with the chain at startup, we found that it would faithfully carry out an instruction it should never accept. If the chain reported that it held no user profiles at all — the kind of answer a node gives while it is starting up, misconfigured, or pointed somewhere unexpected — the indexer concluded that every user on the platform had been deleted and marked them accordingly. A momentary bad answer could therefore erase everyone. The synchronisation now refuses an empty answer outright when it already knows about users, and stops if a single pass would remove more than a small fraction of them. A genuinely new network with no users still starts normally, and the ordinary trickle of departing accounts is untouched, so the guard only fires on the shape of an answer that should never be believed.

### Governance actions that cannot go missing quietly

We also closed a gap where the indexer could accept a governance proposal and silently drop part of it. It only recorded the kinds of decisions it already knew how to represent and ignored the rest, so a newly added kind of action would have passed through governance, taken effect on the chain, and left no trace in the record everyone reads. That silence is now an error: an unrecognised Mirage action stops the block loudly instead of disappearing. Alongside it, a handful of smaller robustness fixes went in — the network calls the indexer makes while collecting balances now have an overall time limit rather than only a per-call one, a very deep comment thread can no longer make one block's work grow without bound, an interrupted indexer reports that it was interrupted instead of appearing to have shut down cleanly, and turning the indexer off in configuration now simply turns it off rather than producing a crash loop that looks like a fault.

### Tested by breaking them on purpose, and honest about what is left

Every fix here ships with a test, and we checked those tests the only way that means anything: by putting each bug back and confirming the tests failed. The ones covering database behaviour run against a real database in a scratch area rather than merely inspecting the code, because a safeguard that is present but broken would satisfy the weaker check. Two known limitations stay on the record rather than being quietly dropped. Some profile information is still fetched from the chain while a block is being written, which we improved but did not eliminate, because removing it entirely would have meant duplicating logic that an earlier security fix deliberately consolidated in one place. And when a node indexes old blocks, it still describes them using today's settings rather than the settings in force at the time, so replayed history can differ in detail from what was originally recorded. Neither is exploitable, and both are written down. Nothing in this release changes chain code, so mixed versions will not disagree about the chain itself — but they will disagree about the index, which is why it still goes out as one coordinated upgrade across the whole fleet.
