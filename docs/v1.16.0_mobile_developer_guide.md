# Mirage v1.16.0 — Mobile Developer Guide

This document covers every API and data model change in v1.16.0 that affects the mobile client. It is written against the backend REST API (base URL: your node's `/api/` prefix).

---

## 1. Tier System Overhaul

The old four-tier system (Free / Trusted / Established / Distinguished) is replaced with three tiers. **Every reference to the old tier names, indices, and levels must be updated.**

### New Tiers

| Tier       | Level | Period Fee (umirage) | MIRAGE equivalent |
|------------|------:|---------------------:|------------------:|
| Free       |     0 |                    0 |                 0 |
| Subscriber |     1 |      100,000,000,000 |           100,000 |
| Agent      |    10 |      500,000,000,000 |           500,000 |

Admin accounts (level >= 100) still exist but are not a user-selectable tier.

### Level-to-Tier-Index Mapping

The chain stores tiers as an ordered array with indices `[0, 1, 2]`. To look up a user's tier config from their `level`:

```
level  0         → tier index 0 (Free)
level  1         → tier index 1 (Subscriber)
level 10         → tier index 2 (Agent)
level >= 100     → tier index 2 (admin, uses Agent limits)
```

**Breaking change**: Previously, levels 1/2/3 mapped to indices 1/2/3. Now levels 1, 2, 3 from pre-upgrade accounts are all remapped to level 1 (Subscriber). Level 10 is the only way to be an Agent.

### Tier Limits per Tier

These come from the chain params endpoint (`GET /mirage/core/v1/params`) in the `tiers` array. Key fields per `TierConfig`:

| Field                  | Free | Subscriber | Agent |
|------------------------|-----:|-----------:|------:|
| `max_content_length`   | 1000 |     20,000 | 20,000 |
| `max_followed_users`   |   25 |        500 |    500 |
| `max_followed_topics`  |   25 |        500 |    500 |
| `max_blocked_users`    |   25 |        500 |    500 |
| `max_blocked_posts`    |   25 |        500 |    500 |
| `max_blocked_topics`   |   25 |        500 |    500 |
| `max_enabled_agents`   |    5 |         50 |     50 |
| `vote_weight`          |  1.0 |       1.33 |   1.33 |
| `can_be_agent`         |   no |         no |    yes |
| `can_remove_anon`      |   no |        yes |    yes |
| `can_have_biography`   |   no |        yes |    yes |
| `can_have_avatar`      |   no |        yes |    yes |
| `can_have_banner`      |   no |        yes |    yes |
| `can_have_flair`       |   no |        yes |    yes |

### Removed TierConfig Fields

These fields no longer exist on `TierConfig`:

- `max_followed_mods` → replaced by `max_enabled_agents`
- `archive_duration_days` → removed
- `eligible_for_mod` → replaced by `can_be_agent`
- `can_change_name` → replaced by `can_remove_anon`

### Anon Prefix Rule

Free accounts always carry an `Anon-` prefix on their username. Subscriber and Agent accounts can remove it (set any username). The mobile client should reflect this: if `user.level == 0`, the username displayed should have `Anon-` prepended if it isn't already.

## 2. New Profile Fields

### `GET /api/get_profile?address=<addr>`

The response now includes these new scalar fields:

```json
{
  "owner": "mirage1abc...",
  "username": "alice",
  "level": 1,
  "created_at": 1709900000,
  "subscription_expiry": 1712500000,
  "auto_renew": true,
  "reserve_funds": 5000000,
  "flair": "",
  "biography": "Hello, I care about open networks.",
  "avatar": "",
  "banner": "",
  "enabled_agents": ["mirage1agent1...", "mirage1agent2..."],
  "followed_users": ["mirage1bob..."],
  "followed_topics": ["crypto", "music"],
  "blocked_users": [],
  "blocked_posts": [],
  "blocked_topics": [],
  "balance": 1500000000
}
```

**New fields (v1.16.0)**:

| Field       | Type   | Notes |
|-------------|--------|-------|
| `biography` | string | Up to 512 characters. Empty string if not set. Only available for Subscriber+ (`can_have_biography`). |
| `avatar`    | string | URL or empty. Only for Subscriber+. |
| `banner`    | string | URL or empty. Only for Subscriber+. |
| `flair`     | string | Empty for now (reserved for future use). |

**Renamed list fields**:

| Old (v1.15.x)         | New (v1.16.0)      |
|-----------------------|--------------------|
| `followed_moderators` | `enabled_agents`   |

The `enabled_agents` array is **ordered by priority** — the first agent has the highest priority when overlays conflict. The list comes from the indexer (full history, not chain-limited), ordered by the user's chosen position.

## 3. New API Endpoints

### 3.1 `POST /api/core/set_biography`

Set or update the user's biography. Subscriber+ only (Free users get rejected by the chain).

**Request body**:

```json
{
  "pubkey": "<base64 compressed secp256k1 pubkey, 33 bytes>",
  "signature": "<base64 ed25519/secp256k1 signature, 64 bytes>",
  "biography": "My new bio text",
  "last_block_hash": "<64-char hex>",
  "pow_difficulty": 0,
  "pow": 0,
  "timestamp": 1709900000
}
```

**Rules**:
- `biography` max 512 characters. Empty string to clear.
- Control characters are rejected.
- Subscribers/Agents: set `pow_difficulty` and `pow` to `0`. PoW is **not allowed** for subscribers.
- Free users: must provide valid PoW (but the chain rejects biography for Free tier, so this is effectively subscriber-only).
- `timestamp`: unix seconds, required.

**Success response**:

```json
{
  "tx_hash": "A1B2C3...",
  "code": 0,
  "height": 12345,
  "raw_log": ""
}
```

**Error response**:

```json
{ "error": "biography too long" }
```

### 3.2 `POST /api/core/set_agents`

Atomically replace the user's entire enabled agents list. This is a **full replacement**, not add/remove — send the complete ordered list every time.

**Request body**:

```json
{
  "pubkey": "<base64>",
  "signature": "<base64>",
  "agents": [
    "mirage1agent_highest_priority...",
    "mirage1agent_second..."
  ],
  "last_block_hash": "<64-char hex>",
  "pow_difficulty": 0,
  "pow": 0,
  "timestamp": 1709900000
}
```

**Rules**:
- `agents`: array of mirage addresses (lowercase). Order matters (first = highest priority).
- No duplicates allowed.
- Cannot include self (`"cannot set yourself as an agent"`).
- Max length enforced from tier config (`max_enabled_agents`): 5 for Free, 50 for Subscriber/Agent.
- Empty array `[]` to disable all agents.
- Subscribers/Agents: `pow_difficulty` and `pow` must be `0`.
- Free users: must provide valid PoW.

**Success response**: same shape as `set_biography`.

**Validation errors**:
- `"agents must be an array"` — 400
- `"invalid agent address: ..."` — 400
- `"duplicate agent: ..."` — 400
- `"cannot set yourself as an agent"` — 400
- `"too many agents: X > Y"` — 400

### 3.3 `POST /api/core/annotate`

Agent-only endpoint. Creates an overlay annotation on an existing post. Only accounts with level 10 (Agent tier) and an active subscription can call this.

**Request body**:

```json
{
  "pubkey": "<base64>",
  "signature": "<base64>",
  "override": "<64-char hex txhash of the target post>",
  "topic": ".",
  "title": "Corrected: actual headline",
  "content": ".",
  "tag": ".",
  "media": ["."],
  "appendix": "Context: this claim was debunked in 2024.",
  "last_block_hash": "<64-char hex>",
  "pow_difficulty": 0,
  "pow": 0,
  "timestamp": 1709900000
}
```

**Sentinel value `"."`**: means "no change" for that field. Use `"."` to leave a field untouched. Use an empty string `""` to **clear** the field. This distinction is important:

| Value sent | Meaning |
|------------|---------|
| `"."`      | Do not modify this field (keep original) |
| `""`       | Clear this field (set to empty) |
| Any other  | Replace with this value |

**Field details**:
- `override` (required): txhash of the post being annotated. Must exist.
- `topic`: replacement topic or sentinel.
- `title`: replacement title or sentinel.
- `content`: replacement content or sentinel.
- `tag`: replacement tag or sentinel. Must be a valid tag if not sentinel.
- `media`: replacement media list or `["."]` for no change. Max 10 items, each max 2048 chars, must use `https://`.
- `appendix`: text appended below the original post. Not a replacement — all agent appendices stack. Use `""` for no appendix.
- PoW must be `0` (agents are subscribers; PoW is rejected).

**Success response**: same shape as other core endpoints.

**Errors**:
- `"agent tier required"` — 403 (caller is not level 10)
- `"override not found"` — 404 (target post doesn't exist)
- `"pow not allowed for agents"` — 400

### 3.4 `GET /api/get_agents`

List all active Agent-tier profiles on the network. No authentication required.

**Response**:

```json
{
  "agents": [
    {
      "address": "mirage1abc...",
      "username": "factchecker",
      "biography": "I verify claims on the network.",
      "avatar": ""
    }
  ]
}
```

**Filters applied server-side**:
- `level = 10` only
- `subscription_expiry > now` (active subscription)
- `deleted_at IS NULL` (not deleted)
- Sorted alphabetically by username (falling back to address if no username)

## 4. Agent Overlay System (How Posts Change)

When a user has enabled agents, every post they view may be modified by agent overlays. This happens server-side — the post objects in feed and detail responses include overlay data.

### New Fields on Post Objects

Any post in a feed response (`/api/get_posts`, `/api/get_post`, `/api/get_user_posts`, etc.) can include these additional fields:

```json
{
  "post_id": "a1b2c3...",
  "topic": "news",
  "title": "Agent-corrected title",
  "content": "Original content here...",
  "tag": "opinion",
  "media": [],
  "agent_edited": true,
  "agent_edits_meta": {
    "title": "mirage1agent_who_changed_title..."
  },
  "appendices": [
    {
      "agent": "mirage1factchecker...",
      "text": "Note: the original claim was misleading. See source: ..."
    }
  ]
}
```

| Field              | Type    | Present when       | Description |
|--------------------|---------|--------------------|-------------|
| `agent_edited`     | bool    | Post was modified  | `true` if any agent overlay was applied |
| `agent_edits_meta` | object  | Post was modified  | Map of `field_name → agent_address` for each replaced field |
| `appendices`       | array   | Post was modified  | List of `{ agent, text }` objects — one per agent that added an appendix |

### Overlay Priority

When multiple agents modify the same field on the same post, the viewer's agent **priority order** (from their `enabled_agents` list) determines which edit wins. For replacement fields (`topic`, `title`, `content`, `tag`, `media`), the first agent (highest priority) that provides a non-null edit wins. For `appendix`, all agent appendices are collected in priority order and all displayed.

### Display Recommendations

1. Show an "agent modified" indicator on posts where `agent_edited == true`.
2. Render appendices below the post content with a visual separator (e.g., left border accent).
3. Consider showing which agent modified which field using `agent_edits_meta` (optional, for power users).
4. Appendices should render as Markdown.

## 5. Username Requirement

**Breaking change**: Every user-initiated transaction on the chain now requires the user to have a username set first. If the user hasn't set a username, the chain rejects the transaction.

Affected actions: posting, voting, following, blocking, awarding, sending tokens, upgrading subscription, setting biography, managing agents, annotating, deleting — everything except `set_username` itself.

**Mobile impact**: Before allowing any action, check that the user has a non-empty username. If not, prompt them to set one first. The error from the chain will include a message about requiring a username, but catching this client-side provides a better UX.

## 6. Removed / Renamed Endpoints

| Old (v1.15.x)                     | New (v1.16.0)                | Notes |
|-----------------------------------|------------------------------|-------|
| `POST /api/core/follow_moderator`   | `POST /api/core/enable_agent`  | Same envelope format; field `moderator` → `agent` |
| `POST /api/core/unfollow_moderator` | `POST /api/core/disable_agent` | Same envelope format; field `moderator` → `agent` |

**Note**: `enable_agent` and `disable_agent` still exist as individual add/remove operations, but `set_agents` (full list replacement) is preferred for the mobile client since it handles reordering atomically.

## 7. Economic Parameter Changes

### Gas Price Reduction

| Parameter            | v1.15.x | v1.16.0 |
|----------------------|--------:|--------:|
| `relay_min_gas_price`| 5,000   | 1,000   |
| `relay_max_gas_fee`  | —       | 500 MIRAGE per message |

Gas is now metered **per message** instead of per transaction. If the backend batches multiple messages into one transaction, each message is charged only for its own gas, capped at 500 MIRAGE. This doesn't require mobile changes since gas is handled server-side, but it means actions are cheaper for users.

### Subscription Reserve

| Parameter                      | v1.15.x | v1.16.0 |
|--------------------------------|--------:|--------:|
| `subscription_reserve_percent` | 0.80    | 0.95    |

95% of the subscription fee now goes into the user's relay gas reserve (up from 80%).

### Vote Weights

| Tier       | Weight |
|------------|-------:|
| Free       |   1.00 |
| Subscriber |   1.33 |
| Agent      |   1.33 |

Previously there were four weights for four tiers. Now just two values.

### Reward Multiplier

The reward multiplier now counts flash quests and achievements alongside daily quests. The formula is `min(5.0, total_completed / 10.0)` — reaching 5x at 50 completed quests of any type.

## 8. Profile List Behavior: Hard Cap vs Deque

Understanding how list limits work is important for the mobile UX:

### Hard-capped lists (transaction rejected when full)
- `enabled_agents`
- `followed_users`
- `followed_topics`

When the user hits the tier limit, the chain rejects the transaction. The mobile client should check the current count against the tier limit and show an appropriate message ("You've reached your limit of X. Remove one to add another.").

### Deque lists (oldest entry silently evicted)
- `blocked_users`
- `blocked_posts`
- `blocked_topics`

When the user exceeds the limit, the oldest entry is silently dropped. The mobile client doesn't need to enforce limits here, but should be aware that very old blocks may disappear from the chain view. The indexer stores up to 100,000 entries per user per list for feed filtering purposes.

## 10. Canonical Envelope Signing

The signing format for new message types follows the same canonical envelope pattern as existing messages. For `MsgSetBiography`, `MsgSetAgents`, and `MsgAnnotate`, the canonical bytes are constructed as:

```
canon_base = concat(
  pubkey_bytes,
  block_hash_bytes,
  difficulty_le64,
  timestamp_le64,
  ...message-specific fields...
)
signed_bytes = concat(canon_base, pow_le64)
signature = sign(signed_bytes)
```

### MsgSetBiography canonical fields (after envelope prefix):
1. `target` (user address, UTF-8)
2. `biography` (UTF-8)

### MsgSetAgents canonical fields:
1. `target` (user address, UTF-8)
2. Each agent address concatenated in order (UTF-8)

### MsgAnnotate canonical fields:
1. `topic` (UTF-8)
2. `title` (UTF-8)
3. `content` (UTF-8)
4. `tag` (UTF-8)
5. `override` (UTF-8)
6. Each media item concatenated in order (UTF-8)
7. `appendix` (UTF-8)

Refer to `shared/canon.py` for the exact byte layout if implementing client-side signing.

## 12. Summary of Breaking Changes

1. **Tier levels changed**: Levels 2, 3 no longer exist. Map old user levels 1/2/3 → Subscriber (1). Level 10 = Agent.
2. **`followed_moderators` → `enabled_agents`**: Field renamed in profile response.
3. **`follow_moderator` / `unfollow_moderator` endpoints removed**: Use `enable_agent`, `disable_agent`, or `set_agents`.
4. **Username required**: All transactions except `set_username` require a username to be set first.
5. **TierConfig fields renamed/removed**: `eligible_for_mod` → `can_be_agent`, `can_change_name` → `can_remove_anon`, `max_followed_mods` → `max_enabled_agents`, `archive_duration_days` removed.
6. **Upgrade level values changed**: Only `1` (Subscriber) and `10` (Agent) are valid.
7. **New post fields**: `agent_edited`, `agent_edits_meta`, `appendices` may appear on any post in feed responses.
8. **New profile fields**: `biography`, `avatar`, `banner`, `flair` added to `get_profile` response.
