# Blockchain Security Review (Full)

Date: 2026-03-08
Scope: `blockchain/` — all Go source: ante handlers, core module, bridge handlers, orchestrator, proto definitions, types, keeper, tests.
Out of scope: `web/`, `indexer/`, `deploy/`, external Solana programs.

## Summary

Full security review of the `blockchain/` project covering 91 files across ante handlers, core module message handlers, bridge logic, orchestrator, proto definitions, and tests. Reviewed code line-by-line, cross-referenced findings with existing tests, then performed a second deep-dive pass targeting cross-message attacks, economic exploits, event spoofing, KV injection, integer edge cases, genesis manipulation, and upgrade handler safety.

**Findings: 3 Critical, 4 High, 9 Medium, 8 Low, 5 Informational.**

## Critical findings

### C-1: Agent-tier subscription never expires (permanent free access)

`module.go` line 761 in `processSubscriptions`:
```go
if core.Level <= 0 || int(core.Level) >= len(params.Tiers) {
    continue
}
```

There are 3 tiers (indices 0, 1, 2), so `len(params.Tiers) = 3`. Agent level is 10. `10 >= 3` evaluates to true, causing the function to `continue` — skipping ALL renewal and downgrade logic for Agent users.

But the subscription index was already removed at line 724 (unconditionally for all expired subscriptions), and the reserve was already burned from the module account at lines 750-757. Because `continue` skips the `saveProfile` label at line 892, the profile is never saved. The result:

1. Subscription index: **removed** (user is never picked up by `processSubscriptions` again)
2. Module account: **reserve tokens burned** (gone permanently)
3. Profile: **not saved** — level stays 10, `ReserveFunds` still shows the old value (ghost reserve)
4. User retains Agent-tier access permanently after a single payment

Additionally, the ghost reserve creates an accounting deficit: the module account no longer holds those tokens, but the profile still claims them. Subsequent `deductRelayGasFee` calls will try to burn from the module account against the phantom reserve, silently failing.

The code has `LevelToTierIndex()` which correctly maps level 10 → tier index 2, but `processSubscriptions` does not use it.

Recommendation: Replace the bounds check with `LevelToTierIndex`:
```go
tierIdx := types.LevelToTierIndex(int(core.Level))
if tierIdx <= 0 {
    continue
}
```

### C-2: Solana burn event forgery via unscoped log parsing

`watcher.go` lines 385-401: `parseBurnsFromSignature` parses ALL `Program data:` log lines from a Solana transaction without verifying which program emitted them.

On Solana, `GetSignaturesForAddress(programID)` returns any transaction where the program ID appears in the account keys — including as a read-only account. A malicious Solana program can:

1. Include the bridge program ID as a read-only account in a transaction
2. Emit `Program data:` log lines matching the `BurnInitiated` event discriminator (which is publicly derivable: `SHA256("event:BurnInitiated")[:8]`)
3. Set any `amount`, `mirage_recipient`, and `burn_id` in the forged event data

Every validator's orchestrator would parse the same fake event and independently submit `MsgBridgeAttestBurned` to Mirage. Once the attestation threshold is met, tokens are minted with no corresponding real burn.

Recommendation: Only process `Program data:` lines that fall within the bridge program's invocation scope. Solana logs have the structure `Program <ID> invoke [N]` / `Program <ID> success` — track the invocation stack and only parse data lines when the bridge program is the current invocation context.

### C-3: Solana watcher processes logs from failed transactions

`watcher.go` lines 380-382: The watcher checks `tx == nil || tx.Meta == nil` but does NOT check `tx.Meta.Err`. On Solana, failed transactions are recorded on-chain with their partial log output. A transaction that emitted a `BurnInitiated` log but subsequently reverted (no actual burn finalized) would still be parsed and attested.

Recommendation: Add `if tx.Meta.Err != nil { return nil, nil }` before parsing logs.

## High findings

### H-1: No on-chain replay protection for relay envelopes

The relay ante chain (`app.go` lines 252-354) bypasses the standard SDK `SigVerificationDecorator`, which means no account sequence number is checked. Envelope replay protection relies solely on timestamp freshness (`max_envelope_age`, ~60s) and block hash window.

Within the validity window, an identical signed envelope can be embedded in multiple distinct outer SDK transactions (varying gas/fee fields), producing different tx hashes. CometBFT mempool deduplication works on tx hash, so these would not be deduplicated.

Impact: For `MsgSendTokens` and `MsgBridgeBurn`, repeated token transfers or bridge burns. The relay operator is trusted infrastructure, but the relay ante chain does not verify outer SDK signatures, so an attacker who observes the mempool P2P traffic could construct replays.

Recommendation: Add a client-generated nonce to the signed canonical bytes and track used `hash(pubkey || nonce)` pairs in a TTL store.

### H-2: Orchestrator watcher goroutines fail silently

In `attestor.go` lines 70-83, watcher goroutine failures are logged but do not cancel the context or signal the main loop. The orchestrator continues running in a degraded state. No WebSocket reconnection for either Mirage burns or Solana confirmations.

Recommendation: Propagate failures via error channel or context cancellation. Add reconnection with exponential backoff.

### H-3: First-writer-wins attestation poisoning

A rogue validator who observes a Solana burn in the mempool can front-run honest validators by submitting `MsgBridgeAttestBurned` with a **different recipient address**. The first attestation creates the record (via `GetOrCreateBridgeAttestation`). All honest validators then fail with "recipient mismatch" (line 241-242). The attestation can never reach threshold.

Impact: Denial of service on individual inbound burns. A single malicious validator can block any Solana→Mirage transfer. Funds are locked (not stolen).

Recommendation: Either reject conflicting parameters and allow a new attestation to be created, or require the attestation parameters to be committed to before reveal (commit-reveal scheme).

### H-4: Upgrade handler list migration errors swallowed — data loss

`upgrades.go` line 186-188 (v1.3.0): List migration setters discard errors:
```go
_ = lm.setter(sdkCtx, owner, items)
```
If a list write fails, the list was already deleted from the profile JSON (line 191: `delete(m, lm.field)`) but never written to the new storage prefix — permanent data loss. The handler returns success, so the SDK commits the partial state.

Recommendation: Propagate errors from list setter calls so the SDK rolls back the entire upgrade on failure.

## Medium findings

### M-1: float64 arithmetic for bridge attestation threshold

`types/bridge.go` lines 208-213: `int64(float64(totalPower) * threshold)` — consensus-breaking risk from non-deterministic float truncation across architectures.

Recommendation: Use integer-only arithmetic or `sdkmath.LegacyDec`.

### M-2: Data race on PowDecorator shared fields

`ante_pow.go` lines 211-213: `d.Window` and `d.DefaultDifficulty` written without mutex during concurrent `CheckTx`.

Recommendation: Use local variables instead of struct fields.

### M-3: MsgDeleteUser missing from relay signature verification

`MsgDeleteUser` routes through the standard SDK ante handler but the inner `envelope_signature` is never cryptographically verified on-chain. The handler only checks `pubkey → address` derivation.

Recommendation: Add `MsgDeleteUser` to the relay detection list and `RelaySigDecorator`.

### M-4: ProcessProposal unconditional pass-through

All proposed blocks are accepted without validation. A malicious proposer can stuff blocks with invalid transactions.

Recommendation: Add basic decode/structural validation.

### M-5: Verbose PoW error messages leak internal state

PoW rejection errors expose current difficulty, grace period, block height, hash, and salt.

Recommendation: Generic client errors; detailed server-side logs only.

### M-6: Orchestrator reads Solana private key from disk on every mint

`minter.go` lines 37-41: TOCTOU risk and unnecessary I/O.

Recommendation: Load once at startup.

### M-7: Anon prefix retained after subscription expiry

When a subscription expires via `processSubscriptions` or `deductRelayGasFee`, the user is downgraded to level 0 but their username is NOT reset to enforce the `Anon-` prefix. The Anon prefix is only enforced at `SetUsername` time.

Attack scenario: User upgrades, sets username "TrustedModerator", lets subscription expire. They retain the non-Anon username at free tier, potentially impersonating a paid user.

Recommendation: Either re-apply the Anon prefix when downgrading, or ensure the UI checks current level rather than relying on username prefix.

### M-8: SubscriptionPeriod=0 governance attack

If governance changes `SubscriptionPeriod` to 0 (`module.go` line 729-732), all expired subscriptions hit `continue` before renewal/downgrade logic. Combined with the subscription index already being removed (line 724), users keep their level permanently. `Validate()` does not require `SubscriptionPeriod > 0`.

Recommendation: Validate `SubscriptionPeriod > 0` in `Validate()`.

### M-9: Admin unlimited free awards with no dedup

Admins (level >= 100) pay zero award cost (`module.go` lines 3318-3328), combined with silent gas fee failure (lines 283-315), enabling unlimited free awards. No per-address per-target deduplication exists — an admin can award the same post repeatedly.

Recommendation: Add per-address per-target deduplication and/or per-block rate limits.

## Low findings

### L-1: UpdateParams cannot set certain fields to zero

`module.go` line 1072: Partial-update uses `!= 0` checks, preventing governance from zeroing `MintDynamicSplit`, `SubscriptionReservePercent`, etc.

### L-2: MsgSetLevel dead code in RelaySigDecorator

`MsgSetLevel` has signature validation code in `RelaySigDecorator` but is not in the relay detection list. Unreachable dead code.

### L-3: Proto reserved tags use comments instead of keyword

`params.proto` tags 6, 11-33, 46-49 reserved via comments only. Compiler won't prevent accidental reuse.

### L-4: Duplicate validateMsgPostMedia call

`Post` handler calls `validateMsgPostMedia` twice.

### L-5: Orchestrator seenSig pruning creates dedup gap

`watcher.go` line 325: Full map clear on 10K entries can cause re-processing of recent signatures. Chain rejects duplicates but gas is wasted.

### L-6: `destChain` in `bridgeAttestMinted` lacks `/` rejection

Unlike `burnID` in `bridgeAttestBurned` (which explicitly rejects `/`), `destChain` in `bridgeAttestMinted` only checks emptiness and length. A crafted `destChain` containing `/` could create confusing KV keys. Mitigated by the burn record existence gate (chain whitelist validated at burn time).

Recommendation: Add explicit `/` rejection for defense-in-depth.

### L-7: No minimum bridge amount

`bridge_handlers.go` line 98: The only check is `amount > bridgeFee`. A burn with `amount = bridgeFee + 1` costs validator resources for 1 umirage of value, enabling dust bridge attacks.

### L-8: deductRelayGasFee swallows SetProfileCore errors

`module.go` lines 397-399: If `SetProfileCore` fails after `BurnFromModuleAmount` succeeded, tokens are burned from the module account but the profile reserve decrement is not persisted — permanent accounting deficit.

## Informational

### I-1: Delete authorization enforced by indexer (confirmed design)

Same as previous review.

### I-2: Bridge is devnet-only (confirmed design)

C-2, C-3, and H-3 become urgent if the bridge is promoted to production.

### I-3: Orchestrator gRPC uses insecure transport

Acceptable for localhost; document for production multi-host setups.

### I-4: Orchestrator permanent error detection via string matching

Fragile pattern; could silently drop burns if error messages change.

### I-5: Fee collector burned before distribution (design choice)

`BeginBlock` burns the entire fee collector balance before the SDK distribution module runs. Validators receive zero native fee revenue — all income comes from `MintIfNeeded`. Intentional deflationary design but should be documented.

## Controls observed

All controls from the initial pass confirmed, plus:
- Username validation: ASCII alphanumeric only (`^[A-Za-z0-9-]+$`), case-insensitive uniqueness — eliminates Unicode confusable attacks.
- Topic validation: strict lowercase alphanumeric. Tag validation: exact whitelist match.
- KV key construction: `burnID` has explicit `/` rejection, sequence IDs are numeric-only, addresses are bech32-validated, count/seq suffixes use `\x00` separator.
- Cross-message attacks within a single tx are safe: `MsgSetUsername` + action works because Cosmos SDK sequential execution is correct behavior; double `MsgBridgeBurn` atomically increments sequence and checks balance.
- Integer overflow: `calculateRelayFee` has proper overflow guard; relay credit uses `sdkmath.Int` with uint64 saturation.
- `ExportGenesis` captures ALL KV pairs via `Iterator(nil, nil)` — comprehensive export.
- `LevelToTierIndex` correctly maps non-contiguous levels (0, 1, 10, 100+) to tier indices — but `processSubscriptions` does not use it (C-1).

1. **C-1**: Fix `processSubscriptions` level check — use `LevelToTierIndex()` instead of raw `int(core.Level) >= len(params.Tiers)`. Also reconcile module account ghost reserves for any affected Agent users.

3. **C-3**: Reject failed Solana transactions (`tx.Meta.Err != nil`).
