## Executive Summary

Full source-code security review of the `blockchain/` project covering 113 tracked Go/proto/module files (139 if generated `*.pb.go` are included). Reviewed transaction admission, the new top-level ante router, relay and standard SDK ante chains, PoW decorator (rewritten to consume an on-chain recent-block-hash window), core message handlers, BeginBlock/EndBlock determinism contracts, mint distribution, the v1.25.0 upgrade handler, dormant bridge surface, and the consensus-determinism regression test suite.

**The single most important shift since the previous review is a deliberate reversal of the v1.24.0 "never-halt" invariant for consensus-critical decode paths.** A real production divergence at `mirage.talk` height 4,349,996 on May 4, 2026 was traced to exactly the silent-fallback behavior that v1.24.0 had introduced as M-1's accepted-risk remediation: a single node hit a transient store read failure inside `GetParams`, fell back to `DefaultParams()` while every peer used the stored params, and emitted a divergent app-hash on the next consensus round. The fix shipped in the v1.24.x binary on `prod` (the v1.25.0 governance-coordinated upgrade has already executed) and is live today. It bakes in:

1. `GetParams` panics with tagged `CONSENSUS_FATAL:PARAMS_*` on store-get / empty / unmarshal / validate failure (no `DefaultParams()` fallback).
2. `deductRelayGasFee`, `processSubscriptions`, `getUserLevel`, `checkReserveOrDowngrade` return tagged `CONSENSUS_FATAL:PROFILE_*` errors on profile read/decode/missing failures.
3. `EndBlock` propagates iterator failures from `GetExpiredSubscriptions` and decode failures from `processSubscriptions` instead of silently continuing.
4. A new on-chain rolling block-hash window (`types.RecentBlockHashesKey`) replaces the per-process in-memory cache that previously caused PoW restart-vs-warm-node divergence.

No new critical or high-severity vulnerability was found. The new fail-fast contract is the right direction; the residual concerns below are about scoping where it is and is not applied, and about a small number of remaining silent-skip patterns adjacent to the consensus path.

**Ship blockers:** None for current non-bridge operation. The v1.25.0 fail-fast cutover is already behind us on prod; no halt occurred during or after the upgrade, which empirically validates that no validator had corrupt params bytes at the upgrade height.

## Findings

### M-1: BeginBlock Reserved Module Account Profile Bootstrap Silently Discards Errors (Medium)

**Location:** `x/core/module/module.go` lines 681–690.

```go
for _, modName := range reservedModuleAccountNames() {
    addr := authtypes.NewModuleAddress(modName).String()
    if _, found, _ := am.k.GetProfileCore(sdkCtx, addr); !found {
        username := reservedUsernameForModule(modName)
        _ = am.k.ClaimUsername(sdkCtx, username, addr)
        if bz, err := json.Marshal(types.ProfileCore{Owner: addr, Username: username}); err == nil {
            _ = am.k.SetProfileCore(sdkCtx, addr, bz)
        }
    }
}
```

This is the same silent-skip pattern that produced the May 4 divergence at scale. Three independent error swallows here:

1. `_, _, _` from `GetProfileCore` — a read error is treated as `found == false`, so the bootstrap path runs even when the row may already exist or when the underlying store is unavailable.
2. `_ = am.k.ClaimUsername(...)` — a write error (e.g., a username collision the chain rejects) is discarded; the next line still writes `ProfileCore` with that username, leaving on-chain state inconsistent (`SetProfileCore` succeeds but `ClaimUsername` did not).
3. `_ = am.k.SetProfileCore(...)` — the symmetric case: username may be claimed but `ProfileCore` write fails. State diverges across nodes if the failure is non-deterministic.

This block is consensus-critical: the reserved-profile bootstrap is exactly the kind of state mutation that, if it succeeds on one node and fails on another, produces app-hash divergence on the very next round.

**Impact:** Latent divergence vector adjacent to the path that caused the May 4 incident. Currently masked because (a) the writes are idempotent and re-attempted every block, and (b) `ClaimUsername`/`SetProfileCore` are simple KV writes that rarely fail in practice. But the design is brittle.

**Remediation:** Either (i) propagate errors to halt the chain, consistent with the new `CONSENSUS_FATAL` contract for everything else in BeginBlock that mutates consensus state, or (ii) gate this whole block behind a "first-block-only" predicate (e.g., a sentinel KV) and run it once at genesis/upgrade rather than every BeginBlock so per-block failures do not accumulate.

### M-2: `MintIfNeeded` `mintAndDistribute` Log-and-Continue Pattern Is the Same Class as the May 4 Vector (Medium, Accepted Risk Recommended)

**Location:** `x/core/keeper/keeper.go` `mintAndDistribute` (helper, ~lines 1295–1345) and `MintIfNeeded` (lines 1280–1660).

`MintIfNeeded` retains the v1.24.0 "never halt the chain" invariant from the prior review's remediation:

- `MintCoins` failure → log and skip the entire mint interval.
- `SendCoinsFromModuleToAccount` failure for one recipient → attempt `BurnCoins` of the skipped portion to keep supply neutral.
- `BurnCoins` failure of the skipped portion → account it as `stuckInModule`, log, continue.
- `IterateValidators` failure → log and skip the interval.
- `LegacyNewDecFromStr(MintDynamicSplit)` failure → log and skip the interval.
- `ResetAllRelayCredits` failure → log and continue (credits carry over).

The contract documents these as "non-divergent because they affect all nodes equally". That is true for purely deterministic input failures (e.g., a bug producing a non-parseable `MintDynamicSplit`). It is **not** true for transient bank/staking I/O failures, which are the same class as the `GetParams` transient read failure that caused the May 4 incident. The same supply state mutations that diverged then can diverge here.

In practice, bank-store I/O failures inside a finalized block are rare and typically indicate node-level disk corruption that produces a clean panic up the SDK stack rather than a recoverable error. So the residual risk is small. But the design choice is inconsistent with the new fail-fast contract elsewhere in BeginBlock.

**Impact:** Latent divergence vector if any of these helper calls returns a non-deterministic error on one node only. Likelihood is low because cosmos-sdk bank operations are deterministic in steady state.

**Remediation:** Either (i) align with the new fail-fast contract — propagate errors from `MintCoins` / `SendCoinsFromModuleToAccount` / `BurnCoins` / `IterateValidators` and halt instead of log-and-continue, or (ii) **explicitly accept** this exception, document the rationale (mint subsystem latency budget vs. liveness halts). The watchdog/auto-recovery surface has now been validated by the v1.25.0 upgrade landing without incident, so option (i) carries less perceived liveness risk than it did at the time of the previous review.

### M-3: Paid Relay Fee Admin Waiver Still Returns Success on `DeductFeeFromOwner` Failure (Medium, Carryover from Previous M-4)

**Location:** `x/core/module/module.go` lines 298–337 (admin branch of `deductRelayGasFee`).

The v1.25.0 fail-fast change reworked `deductRelayGasFee` for paid non-admin users (now correctly returns `CONSENSUS_FATAL:PROFILE_*` on missing/corrupt profile). The admin branch — `level >= 100` — still returns nil silently if `DeductFeeFromOwner` fails:

```go
// ... admin branch ...
if err := am.k.DeductFeeFromOwner(ctx, owner, fee); err != nil {
    ctx.Logger().Error("admin fee deduction failed; continuing", ...)
    return nil
}
```

The previous review documented this as an explicit product choice for admin users. The failure case (admin lacks balance OR underlying bank send fails) can be:

- **Per-node:** transient bank I/O — same divergence vector as M-2.
- **Cross-node deterministic:** the admin's account legitimately lacks funds — all peers see the same outcome, so no divergence, but the admin gets a free relay tx, which is the documented product policy.

**Impact:** Same residual divergence class as M-2, scoped to admin txs. Admin tx volume is low and admins are validators or operators, so blast radius is small.

**Remediation:** As in M-2, either align with the fail-fast contract or document explicit acceptance. If the product wants admins to never block on fee deduction, prefer a cross-cutting "skip fee for admin" branch BEFORE the bank call, so the only reason the bank call would fail is the same on every node.

### M-4: Relay Allowlist Parity Across `isRelayMessage`, `RelaySigDecorator`, PoW Switches (Medium, Carryover from Previous M-8)

**Location:** `app/app.go` lines 75–105 (`isRelayMessage`), `app/ante_metasig.go` `RelaySigDecorator` switches, `app/ante_pow.go` per-message-type AnteHandle switches (substantially refactored to use `routePoWTx` but still per-message).

The previous review's M-8 was not addressed in this cycle. Relay routing, relay signature verification, and PoW handling each maintain their own type switch over the relay message set. `RelaySigDecorator` retains a `default: // ignore others` branch and `MsgSetLevel` still appears in `RelaySigDecorator` despite not being in `isRelayMessage`.

The new top-level `mirageAnteRouter` keeps the previous mixed-tx rejection (which is what made this finding latent rather than active). But the regression surface is the same: a future core message added to one switch but not the others can revive the old class of signature or PoW coverage bugs for that single message.

**Impact:** Latent regression risk for any new relay-eligible message.

**Remediation:** Add a single shared registry of relay messages (a `map[reflect.Type]struct{}` or generated table) and assert at app init that all three switches consume the same registry. Alternatively, a unit test that enumerates `isRelayMessage` returning true for each entry, then walks `RelaySigDecorator`'s switch and the PoW AnteHandle switch to confirm each entry is handled.

### M-5: `processSubscriptions` Performs `RemoveSubscription` Before Profile Decode Check (Medium)

**Location:** `x/core/module/module.go` `processSubscriptions` lines 832–862.

For each expired subscription:

1. `RemoveSubscription` is called first.
2. If `params.SubscriptionPeriod == 0` (one-time payment), the loop continues without renewal — and **without** ever decoding the profile.
3. Otherwise, `GetProfileCore` is called and `CONSENSUS_FATAL:PROFILE_*` errors halt the chain.

Two issues:

1. **One-time-payment short-circuit hides corruption from the fail-fast detector.** A corrupt `ProfileCore` for a user with an expiring one-time-payment subscription is never detected here. This is consensus-safe (no state mutation depends on the corrupt bytes), but it weakens the fail-fast contract's reach. If a different EndBlock path later does decode the same profile, the halt happens then instead.

2. **`RemoveSubscription` failure paths.** Lines 833–836:
   ```go
   if err := am.k.RemoveSubscription(sdkCtx, sub.Address, sub.Expiry); err != nil {
       return fmt.Errorf("processSubscriptions: failed to remove old index for %s: %w", sub.Address, err)
   }
   ```
   This propagates correctly. But if a SetParams change makes `SubscriptionPeriod` toggle from non-zero to zero between the start and end of one EndBlock (impossible in current design, but worth pinning) the path order would matter. The current ordering is safe; a regression test that asserts ordering would be cheap insurance.

**Impact:** Reduced fail-fast coverage on the one-time-payment path; ordering brittleness on the renewal path.

**Remediation:** Move the `GetProfileCore` decode BEFORE the `SubscriptionPeriod == 0` short-circuit. Treat a corrupt expired-subscription profile as halt-worthy regardless of renewal policy. Add a regression test for the one-time-payment-with-corrupt-profile case.

### L-1: Bridge Handler Routing Still Active Despite Dormancy (Low, Bridge Disabled)

**Location:** `x/core/module/bridge_handlers.go` (entire file, dormant banner added but logic unchanged).

Anyone can submit `MsgBridgeBurn` or `MsgBridgeAttestMinted` today; the message is decoded by the chain and routed to the handler, which rejects it inside `ValidateBridgeChain` because `params.BridgeChains` is empty. This is correct defense-in-depth but it is governed solely by params.

If a future params update accidentally added a bridge_chain entry (e.g., a copy-paste in a governance proposal), the dormant code would go live without a code review and without re-running the bridge findings from the previous review (H-2, M-2, M-3, M-6, M-7, L-6) which are all still unfixed.

**Impact:** Risk of accidental bridge re-enable via params alone, with all known bridge-scope findings still latent.

**Remediation:** Add a hard top-level kill-switch — either a dedicated `params.BridgeEnabled bool` (default false, must be explicitly true to dispatch any bridge handler) or an early `if len(params.BridgeChains) == 0 { return error }` plus a unit test that asserts the dormant condition. This protects against accidental governance-only re-enable without a code review.

### L-2: PoW Recent-Block-Hash Window Started Empty at v1.25.0 Upgrade Height (Low, Operational, Already Behind Us)

**Location:** `app/upgrades.go` v1.25.0 handler (intentionally does not pre-populate `RecentBlockHashesKey`) and `app/ante_pow.go` `recentHashSeen`.

The on-chain rolling window started empty at the upgrade height because the handler does not pre-populate it. For `BlockHashWindow` blocks after the upgrade, only envelopes whose `last_block_hash` equaled the current `LastBlockId` were accepted; older but still-recent block hashes were rejected. Clients transparently retry with the new last block hash, so the user-visible impact was a brief PoW UX dip during the cutover.

The window is now full and this is no longer a live concern. Recording the behavior here so future upgrades that introduce a similar fresh-state cache do not have to re-derive the trade-off.

**Remediation:** None required. If a similar fresh-state cache is introduced in a future upgrade, weigh pre-populating it from `ctx.BlockHeader().LastBlockId.Hash` for at least one entry vs. accepting the brief UX dip.

### L-3: `getUserLevel` Returns `(0, "")` for Wrong-Length Pubkey Without Surfacing (Low)

**Location:** `app/ante_pow.go` `getUserLevel` lines 113–116.

```go
if len(pubkey) != 33 {
    return 0, "", nil
}
```

A relay envelope with a 32-byte (or otherwise non-33-byte) `EnvelopePubkey` is silently treated as level 0 / empty address, so it routes through the free-tier PoW branch. Validation happens elsewhere (signature verification will fail because the pubkey is malformed), so this isn't an exploit vector. But it is the same shape as the `getUserLevel` pattern that the previous review flagged as a consensus-divergence vector — silent normalization of a malformed input.

**Impact:** Defense-in-depth weakness only; the malformed envelope will be rejected later in the ante chain.

**Remediation:** Reject malformed pubkey lengths at the top of `AnteHandle` with a clear error, before any `getUserLevel`/`canUsePoW`/`routePoWTx` call. This avoids any future code path that accidentally trusts the (0, "") return as a real user.

### L-5: `routePoWTx` Logs Profile Decode Failures at `Error` Level on Both Branches (Low, Cosmetic)

**Location:** `app/ante_pow.go` `routePoWTx` lines 180–195.

When a profile decode fails inside `canUsePoW` → `getUserLevel`, `routePoWTx` logs at `Error` level and rejects the tx with `CONSENSUS_FATAL:PROFILE_DECODE`. This is correct and matches the new contract.

When a paid user has insufficient reserve, `routePoWTx` also logs at `Error` level. That second case is a normal user-error rejection path, not an incident-class event. Mixing them at the same log severity makes incident triage harder (operators grepping for `CONSENSUS_FATAL` are fine; operators grepping for `Error` will see false positives).

**Impact:** Operator log noise; no consensus or correctness issue.

**Remediation:** Lower the "insufficient reserve" log to `Info` or `Warn`. Reserve `Error` for the consensus-fatal path.

## Positive Security Controls Observed (this cycle)

- **Consensus-determinism-first contract.** Every place that previously substituted defaults on decode failure now panics with a tagged `CONSENSUS_FATAL:*` message including height, key, and byte length for incident triage. The previous `Logger().Error(...)` + silent fallback pattern survived only in non-consensus-critical write paths (mint-subsystem failures, optional counter writes), and those are explicitly documented in `BeginBlock`/`EndBlock` doc comments.
- **On-chain rolling block-hash window** (`types.RecentBlockHashesKey`) eliminates the per-process in-memory PoW cache that caused restart-vs-warm-node divergence. The window is populated by `BeginBlock` from `ctx.BlockHeader().LastBlockId.Hash`, length-bounded by `params.BlockHashWindow`, and read directly by the PoW ante through `GetRecentBlockHashes`. `RecordRecentBlockHash` propagates write failures so BeginBlock halts on a divergent window write rather than silently writing an empty window.
- **Top-level ante router (`mirageAnteRouter`).** Staking-disable policy now runs FIRST, before relay-vs-non-relay classification, so both `stdAnte` and `relayAnte` paths inherit it. The historical bug (a pure non-relay `MsgCancelUnbondingDelegation` bypassing the rule via `stdAnte`) is closed and pinned by `TestMirageAnteRouterRejectsThirdPartyStakingBeforeRouting`.
- **Routing simplification in PoW ante.** Sixteen near-identical per-message branches now share a single `routePoWTx` helper that unifies `canUsePoW` + `checkReserveOrDowngrade`. Less surface area for the M-5/M-8 class of regression.
- **Restart-equivalence test for PoW.** `TestValidatePoWBytesArgon2_RestartEquivalence` pins the contract that "warm" and "freshly restarted" nodes produce identical accept/reject decisions when their on-chain windows are byte-identical.
- **Failure-injection knobs in mock store.** `mockStoreService.{getErrors, setErrors, iterError}` plus the `mintBankIface` interface let tests deterministically simulate every store-failure mode and bank-failure mode without standing up a real store. Used by `consensus_determinism_test.go`, `never_halt_test.go`, `params_test.go`, `mint_distribute_test.go`.
- **Bridge dormancy banners in source.** Every dormant orchestrator/bridge file now begins with a standardized banner explaining the offline state and the security-review scope policy (do NOT surface findings until reactivation). Lowers the risk that future contributors mistake dormant code for production code.
- **v1.24.0 fixes still in place.** Award cost cap, validator-isolated mint, staking-disable router fix, stdAnte construction fail-fast, GetProfiles corruption counter, proto tier comment — all carried forward intact.

## Prioritized Recommendations

1. **Convert the BeginBlock reserved-profile bootstrap to either fail-fast or one-shot init** (M-1). This is the single closest-to-incident-class silent-skip pattern still in the chain.
2. **Decide M-2 explicitly:** keep the mint subsystem on log-and-continue (with a documented rationale), or align with the new fail-fast contract. The current state is contract drift.
3. **Decide M-3 explicitly** for the admin waiver in `deductRelayGasFee`: same shape as M-2.
4. **Add the relay-allowlist parity test** (M-4) so future relay-eligible messages cannot revive the bypass class.
5. **Add a top-level bridge kill-switch** (L-1) so accidental governance-only bridge re-enable cannot bring the dormant code path live without a code review.
6. **Trivial cleanup:** L-5 (log severity).
7. **Periodic params self-audit** wired into the divergence watchdog or a backend health probe — read the `params` row, attempt unmarshal + `Validate()`, alert on failure. The v1.25.0 cutover was clean; a periodic check protects the next governance proposal that triggers `Validate()` mid-block from silently surfacing bit-rot at a less convenient time.
8. **Operator runbook** entry for `CONSENSUS_FATAL:PARAMS_*` halts in `docs/troubleshooting/incident-recovery.md` (state-sync recovery procedure).
