# Blockchain Security Review — 2026-03-12

**Scope:** `blockchain/` — all Go source (ante handlers, core module, bridge, orchestrator, types, keeper, upgrades, proto/types), plus `go.mod`.
**Out of scope:** `web/`, `indexer/`, `deploy/`, external Solana programs.
**Baseline:** v1.18.1, HEAD. Previous review: review-2026-03-09 (v1.18.0).

---

## Executive Summary

Full line-by-line security review of the `blockchain/` project covering ~66 Go source files. Reviewed all ante handler routing, core module message handlers, bridge logic, orchestrator, types/params/keeper, and upgrade handlers.

One critical vulnerability discovered: **mixed relay + SDK messages in a single transaction bypass all signature verification**, enabling unauthorized fund theft from any account. The bank module is registered and its `MsgSend` handler does not re-verify signers — authentication relies entirely on the ante handler, which is bypassed for non-relay messages routed through the relay ante chain.

Previous findings (envelope replay C-1 from review-2026-03-09) confirmed fixed via nonce-based replay protection. Biography length enforcement partially fixed but has a rune vs byte mismatch. The `GetParams` silent fallback to `DefaultParams` violates the project's fail-fast philosophy and could mask state corruption.

**Ship blocker:** C-1 (mixed message signature bypass). Fix is a one-line rejection check in the ante router.

## Findings

### C-1: Mixed Relay + SDK Messages Bypass All Signature Verification — Fund Theft (Critical)

**Location:** `app/app.go` lines 251–352 (ante handler routing), `app/ante_metasig.go` line 958 (`default: // ignore others`)

The ante handler routes transactions to either the standard SDK ante chain (which includes `SigVerificationDecorator`) or the relay ante chain (which does not). The routing decision is made by scanning all messages: if ANY message is a relay type (`MsgPost`, `MsgVote`, `MsgSendTokens`, etc.), the entire transaction enters the relay ante chain. The relay chain's `RelaySigDecorator` only validates relay message types and has `default: // ignore others` for unrecognized messages. The relay chain also lacks `ValidateBasicDecorator`.

The bank module is registered (`app_config.go` line 180) with a full `MsgSend` handler. In Cosmos SDK v0.53, `baseapp.runMsgs()` dispatches each message to its registered handler without re-verifying signers — signer authentication is entirely the ante handler's responsibility.

**Exploit:**
1. Attacker computes valid PoW and creates a legitimate `MsgPost` with their own envelope keypair.
2. Attacker appends `bank.MsgSend{FromAddress: victim, ToAddress: attacker, Amount: X}` to the same transaction.
3. Transaction enters the relay ante chain because it contains `MsgPost`.
4. `PowDecorator` validates `MsgPost` PoW, ignores `MsgSend` (`default:` case).
5. `RelaySigDecorator` validates `MsgPost` envelope signature, ignores `MsgSend` (`default:` case).
6. No `SigVerificationDecorator` runs — the victim's SDK signature is never checked.
7. `baseapp.runMsgs()` executes both: post is created, **victim's funds are transferred to attacker**.

The same attack works with `bank.MsgMultiSend`, `gov.MsgVote`, `authz.MsgGrant`, or any other registered SDK message type. Any message from any module can piggyback on a relay transaction without authorization.

**Severity:** Any network participant can steal funds from any account. Only requires PoW computation (minutes of CPU time) and knowledge of the victim's address.

**Remediation:** Reject transactions that mix relay and non-relay messages. After detecting `containsMeta = true`, verify ALL messages are relay types:

```go
if containsMeta {
    for _, m := range tx.GetMsgs() {
        switch m.(type) {
        case *coretypes.MsgPost, *coretypes.MsgVote, /* ...all relay types... */:
            // ok
        default:
            return ctx, fmt.Errorf("cannot mix relay and non-relay messages in one tx")
        }
    }
}
```

### M-1: `GetParams` Silent Fallback to DefaultParams Masks State Corruption (Medium)

**Location:** `x/core/keeper/keeper.go` lines 1074–1084

```go
_ = k.cdc.Unmarshal(bz, &p)    // unmarshal error silently discarded
if p.MinDifficulty == 0 || ... || len(p.Tiers) == 0 {
    p = types.DefaultParams()   // silent fallback
}
```

Two issues: (1) Unmarshal errors are discarded — corrupted params bytes cause silent revert to defaults. (2) The zero-value heuristic falls back to `DefaultParams()` without any error. If the `params` key is corrupted or partially written, the entire chain silently reverts to default economics (different mint quantities, fees, tier pricing, bridge thresholds) without any governance proposal.

This violates the project's documented "fail fast, no fallbacks" philosophy.

**Remediation:** Return an error when unmarshal fails or the zero-value guard triggers. The only legitimate default-fallback is during genesis (empty store).

### M-2: Biography Length — Rune Count vs Byte Count Mismatch (Medium)

**Location:** `x/core/module/module.go` line 1865 (handler), `x/core/types/types.go` line 95 (`ValidateBasic`)

The `SetBiography` handler validates using character (rune) count:
```go
if maxLen > 0 && uint64(utf8.RuneCountInString(biography)) > maxLen {
```

But `ValidateBasic` (called during `updateProfileCore` → `SetProfileCore`) uses byte count:
```go
if len(p.Biography) > 512 {
```

A 200-character CJK biography (200 runes, 600 bytes) passes the handler check but fails `ValidateBasic`. Users with non-ASCII text are silently denied biographies within their tier limit. Same mismatch exists for `Avatar` (line 98) and `Banner` (line 101).

**Remediation:** Change `ValidateBasic` to use `utf8.RuneCountInString()` for biography, avatar, and banner, matching the handler-level validation. Or change both to byte count — but be consistent.

### M-3: Failed Token Burns Leave Tokens in Module Account (Medium)

**Location:** `x/core/module/module.go` — `deductRelayGasFee` lines 332–338, `processSubscriptions` line 754, `Subscribe` line 3142

When `BurnFromModuleAmount` fails, the code logs a warning but continues to save the reduced reserve to the profile:

```go
core.ReserveFunds -= fee
if err := am.k.BurnFromModuleAmount(ctx, fee); err != nil {
    ctx.Logger().Warn("deductRelayGasFee: failed to burn from module", ...)
}
// profile saved with decremented reserve, but tokens not actually burned
```

Over many transactions, unburned tokens accumulate in the module account — total supply is higher than expected. Same pattern in `checkReserveOrDowngrade` (`ante_pow.go` lines 170–176) where both `RemoveSubscription` and `BurnFromModuleAmount` errors are silently discarded.

**Remediation:** Return the error and roll back the transaction, consistent with the project's fail-fast philosophy.

### M-4: No Upper Bounds on Economic Governance Parameters (Medium)

**Location:** `x/core/types/params.go` — `Validate()` function

Several critical economic parameters have no upper bound validation:

| Parameter | Current validation | Risk |
|-----------|-------------------|------|
| `MintQuantity` | `> 0` only | Governance sets to `math.MaxUint64` → hyperinflation |
| `VoteWeight` (per tier) | `>= 0` only | Single tier gets 10^9 weight → vote manipulation |
| `RelayMinGasPrice` | None | Set to 0 → unlimited free relay spam |
| `RelayMaxGasFee` | None | Set to 0 → fee model breaks |

All require compromised governance (honest-majority assumed), but reasonable ceilings prevent accidental catastrophic misconfiguration.

**Remediation:** Add upper bounds in `Validate()`: `MintQuantity <= 1_000_000_000_000`, `VoteWeight <= 100`, `RelayMinGasPrice > 0`, `RelayMaxGasFee > 0`.

### M-5: Genesis Import Silently Ignores Write Errors (Medium)

**Location:** `x/core/module/module.go` `InitGenesis` lines 506–560

```go
_ = am.k.SetRawKVPair(sdkCtx, key, value)
// ...
_ = am.k.ClaimUsername(sdkCtx, username, owner)
// ...
bz, _ := json.Marshal(ip.Core)
```

If KV writes, username claims, or profile saves fail during genesis import, the chain starts with incomplete state — missing profiles, orphaned subscriptions, or lost data. A corrupted genesis export imports without any error.

**Remediation:** Accumulate errors and panic at the end of `InitGenesis` if any writes failed.

### M-6: Minting Distribution Errors Silently Skip Validators (Medium)

**Location:** `x/core/keeper/keeper.go` lines 1387–1394

```go
if err := k.bank.SendCoinsFromModuleToAccount(ctx, types.ModuleName, accAddr, val_coins); err != nil {
    continue  // minted tokens stay in module account
}
```

Validator address parsing and coin distribution errors are silently skipped. Undistributed tokens accumulate in the module account. If systematic (e.g., module account blocked), all validators receive nothing while tokens are minted.

**Remediation:** Log at Error level. Consider returning an error if all validators fail.

### M-7: Orchestrator `retry()` Silently Drops Burns on `TransactionTooOld` (Medium)

**Location:** `orchestrator/attestor/attestor.go` lines 412–415

```go
if isPermanentError(err) {
    a.logger.Printf("INFO  permanent error (no retry): %v", err)
    return nil  // burn silently dropped
}
```

`ErrTransactionTooOld` causes the burn to be silently discarded. User funds are stuck (burned on Mirage, not minted on Solana) until the orchestrator is restarted and `replayPendingBurns` runs.

**Remediation:** Differentiate between `ErrBridgeMintAlreadyRecorded` (safe to skip) and `ErrTransactionTooOld` (add to retry queue or trigger immediate replay).

### M-8: Swallowed Errors in Historical Upgrade Migrations (Medium)

**Location:** `app/upgrades.go` — multiple locations (lines 93, 187, 196, 1439)

```go
_ = app.CoreKeeper.SetProfile(sdkCtx, owner, nbz)   // error discarded
_ = lm.setter(sdkCtx, owner, items)                   // error discarded
```

Profile and list migration errors are silently discarded. If a profile write fails, the migration reports success but leaves the profile in an inconsistent state. Historical upgrades have already run, but the pattern persists and risks data loss in future migrations.

**Remediation:** For future upgrades, always propagate errors from state-mutation calls.

### L-1: Self-Follow and Self-Block Not Prevented (Low)

**Location:** `x/core/module/module.go` — `FollowUser` (~line 2449), `BlockUser` (~line 2238)

`EnableAgent` correctly prevents self-enabling (`if agent == owner`), but `FollowUser` and `BlockUser` have no equivalent check. A user can block themselves, which removes them from their own followed list and wastes a deque slot.

**Remediation:** Add `if user == owner { return error }` in both handlers.

### L-2: `ValidateBasic` Hardcoded Limits Diverge from Tier Config (Low)

**Location:** `x/core/types/types.go` lines 95–106

Biography (512), avatar (512), banner (512), flair (20) byte limits are hardcoded and don't reference `TierConfig.MaxBiographyLength`. If governance changes tier limits, `ValidateBasic` won't reflect them.

**Remediation:** Pass tier config limits to `ValidateBasic` or remove the hardcoded checks in favor of handler-level validation only.

### L-3: Missing `MsgCancelUnbondingDelegation` in Staking Restriction (Low)

**Location:** `app/ante_disable_staking.go` lines 16–43

`DisableDelegatorStakingDecorator` blocks `MsgBeginRedelegate`, `MsgDelegate`, `MsgUndelegate` (non-self), but does not check `MsgCancelUnbondingDelegation` (present in SDK v0.50+). Practical impact is low since only self-undelegation is permitted.

---

### L-4: Float64 Precision in Reserve Calculations (Low)

**Location:** `x/core/module/module.go` — `processSubscriptions` line 812, `Subscribe` line 3162

```go
reserveAmount := uint64(float64(periodFee) * reserveFrac)
```

Float64 introduces rounding. `uint64(float64(1000000000001) * 0.3)` may not equal exactly `300000000000`. Unlikely at current token scales but violates determinism best practice.

**Remediation:** Use integer arithmetic: `reserveAmount = periodFee * reservePercent / 100`.

### I-3: Nonce Namespace Uses 128-bit Truncated Pubkey Hash (Informational)

**Location:** `app/ante_metasig.go` line 58

`pubHash[:16]` uses 128 bits of SHA-256(pubkey) for nonce namespacing. Birthday collision at ~2^64 — practically infeasible but could use full 32 bytes at the cost of slightly larger KV keys.

### I-4: Orchestrator Signer Indentation Bug (Informational)

**Location:** `orchestrator/mirage/signer.go` lines 348–351

`err` assignment and return not indented to match the `if` block. Functionally correct (Go doesn't use indentation for scoping) but harms readability.

---

### I-5: `ProcessProposal` Performs Only Minimal Validation (Informational)

**Location:** `app/app.go` lines 359–373

`ProcessProposal` only checks that tx bytes are non-empty, decodable, and contain at least one message. It does not run the ante handler. A malicious proposer can stuff blocks with transactions that decode correctly but fail ante validation. Impact is limited to wasted block space — invalid txs fail during Finalize.

## Not a Bug / Accepted Risk

| Item | Status | Rationale |
|------|--------|-----------|
| PoW difficulty float (`math.Pow`) | **By design** | All validators run identical amd64/Go. Cross-architecture divergence is theoretical. |
| Bridge float-to-BPS conversion | **Deprioritized** | Bridge not live (`BridgeChains` empty). Threshold math now uses integer BPS. |
| Duplicate awards on same post | **By design** | Awards stack intentionally. |
| `UpdateParams` cannot set values to zero | **By design** | Partial-update `!= 0` logic is intentional. |
| `PrepareProposal` passes all txs | **Not a live concern** | Proposer tx stuffing wastes execution but is not exploitable for fund theft. |
| Anon prefix on downgrade | **By design** | Username persists across tier changes — a user-chosen identity. |
| `SubscriptionPeriod = 0` | **By design** | Zero period means one-time payment with no renewal. |
| Admin unlimited free awards | **By design** | Admin trust assumption (level >= 100 requires governance). |
| Delete authorization indexer-enforced | **By design** | Chain is pass-through; indexer gates ownership. Documented. |
| No immediate subscription downgrade | **By design** | Users disable auto-renewal and wait for expiry. No refund mechanism. |

## Assumptions

- **Cosmos SDK signer model:** `baseapp.runMsgs()` does not re-verify message signers — signer authentication relies entirely on the ante handler. This is standard SDK behavior as of v0.53.3 and is the root cause of C-1.
- **Bank module active:** `bank.MsgSend` is registered and executable. The bank handler calls `SendCoins(from, to, amount)` without re-checking signer authorization.
- **Validator hardware:** All validators run identical amd64 hardware and Go version. PoW float arithmetic is accepted risk.
- **Governance threat model:** M-4 upper-bound findings require compromised governance. Honest-majority assumed.
- **Bridge not live:** Bridge-specific findings are deprioritized. `BridgeChains` config is empty in production.
- **Indexer trust:** Delete/Edit authorization enforced by indexer, not on-chain.
