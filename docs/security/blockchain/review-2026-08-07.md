## Executive Summary

Re-audited 43 tracked non-test Go/proto files outside patches, 74 including generated files and tests, and 145 Go files in the two vendored forks. Traced transaction routing and both ante chains, fee-payer consent, envelope signatures and nonces, PoW, governance authority, all core handlers, subscription and relay accounting, mint/burn and supply invariants, BeginBlock/EndBlock, profile/list state, delete-user, params/genesis, all upgrade handlers, and patch provenance.

**No new Critical or High issue was found.** No current privilege escalation, signature bypass, unauthorized mint/burn, replay bypass, or third-party fee-drain path was identified. The C-1 outer-signature fix, relay ante ordering, governance-authority rejection, mixed-transaction rejection, bridge hard-rejection, nonce fail-fast behavior, and dual supply invariants all hold.

The five Aug 6 Medium findings remain open. This review adds two Medium findings in the same operational/consensus-safety family:

1. **PoW cleanup marker reads fail open.** A node-local error reading `pow_cleanup_marker` resets that node's cleanup cursor to height 1 while peers advance from the stored marker. BeginBlock logs cleanup errors and continues, so different counter keysets can be committed. See **M-6**.
2. **Governance-safe bounds are incomplete.** `PowMessageWindow`, `SubscriptionPeriod`, and `MaxEnvelopeAge` accept the full `uint64` range but are converted to `int64` or `time.Duration`, or used as loop work. A params update that passes `Validate()` can make EndBlock scan the full chain history or overflow subscription/replay timing. See **M-7**.

Three additional Low write-discard/parameter semantics gaps were confirmed: mutual-exclusion list cleanup ignores deletes (**L-8**), valid zero-valued params cannot be applied through `MsgUpdateParams` (**L-9**), and the admin gas waiver treats every deduction error as insufficient balance (**L-10**).

**Ship blockers:** None. The new Mediums require either a node-local store failure or an approved governance parameter change; neither is a public, unprivileged exploit. **Recommended next release work:** fix M-6 and M-7 first because both are small, auditable changes that close direct chain-progress/divergence hazards. Then address the existing consensus write-discard family together.

## Findings

### M-1: Subscription Index / Profile Saves Log-and-Continue After Value Has Moved (Medium — Open)

**Location:** `x/core/module/module.go:1022–1025`, `1065–1076`, `3398–3421`, `3473–3491`.

EndBlock renewal and both `MsgSubscribe` paths can burn or escrow value, then ignore `RemoveSubscription`, log-and-continue after `SetSubscription`, or log profile-save failures and still return success.

**Impact:** A node-local write failure can commit a subscription index, profile, or bank state different from peers. Deterministic failure can leave a paid user without an expiry index after payment.

**Remediation:** Propagate index/profile write and marshal errors. Reject the user transaction or return a non-nil EndBlock error so the cached state is not committed.

**Tests:** Inject `RemoveSubscription`, `SetSubscription`, and `SetProfileCore` failures after successful burn/escrow; assert no success path commits moved value.

---

### M-2: Tier-Cap Counters Silently Default to Zero on `store.Get` Error (Medium — Open)

**Location:** `x/core/keeper/keeper.go:354–356`, `374–375`, `394–397`, `467–477`, `554–565`; cap checks at `x/core/module/module.go:2144`, `2703`, `2852`.

Count and sequence helpers discard `store.Get` errors and decode the result as zero. These counters gate hard caps for followed users, followed topics, and enabled agents.

**Impact:** A node-local read error can admit an entry past the tier cap, rewrite a real counter from zero, and diverge from peers.

**Remediation:** Return and propagate errors from every count/sequence read. Distinguish an absent key from a failed read.

**Tests:** Inject count/sequence key read failures through each set, ordered-set, and deque path.

---

### M-3: `DeleteUserState` Fail-Opens on Profile Reload and Subscription Removal (Medium — Open)

**Location:** `x/core/keeper/keeper.go:2275–2280`, `2335–2338`; the handler already decodes the profile at `x/core/module/module.go:3018–3029`.

`DeleteUserState` redundantly reloads the profile while discarding Get/unmarshal failures, then discards `RemoveSubscription` errors.

**Impact:** The profile can be deleted while its username mapping or subscription index survives. A stale subscription entry later triggers `CONSENSUS_FATAL:PROFILE_MISSING`; a node-local delete failure can diverge immediately.

**Remediation:** Pass the already-decoded username and expiry into the keeper operation, or fail closed on the reload. Propagate subscription-index removal errors.

**Tests:** Inject profile Get/unmarshal and subscription-delete failures; assert transaction rollback and no orphan keys.

---

### M-4: Period-Zero Expiry Skips Reserve Burn and Tier Downgrade (Medium — Open, Precondition Narrowed)

**Location:** `x/core/module/module.go:916–918`; semantics at `x/core/types/params.go:164–165`.

After removing an expired subscription index and decoding the profile, `SubscriptionPeriod == 0` immediately continues before burning reserve or clearing paid-tier fields.

**Impact:** Existing indexed subscriptions can become permanent paid profiles with stranded reserve after a transition to one-time-payment mode.

**Correction to Aug 6:** The current `MsgUpdateParams` merge treats zero as “not supplied,” so governance cannot presently set `SubscriptionPeriod` to zero through that message. The state is reachable through genesis, raw-state import, or a future upgrade/direct params write. That narrows likelihood but does not make the transition logic correct.

**Remediation:** Always burn leftover reserve and clear paid fields when an indexed subscription expires without renewal, including period-zero mode.

**Tests:** Expire an indexed paid profile under period zero and assert reserve burn, level zero, expiry zero, and no index.

---

### M-5: Consensus Write Failures Are Incorrectly Described as Fleet-Wide (Medium — Open)

**Location:** `x/core/module/module.go:644–648`, `756–760`; concrete discards at `module.go:877` and `x/core/keeper/keeper.go:2036`, `2104`, `2107`.

BeginBlock/EndBlock comments claim relevant write failures “affect ALL nodes equally.” That is true for deterministic logic failures, not node-local database failures.

**Impact:** The comments encode the wrong safety contract and perpetuate log-and-continue behavior on difficulty, PoW-window, and calm-sequence state.

**Remediation:** Rewrite the comments and fail closed on writes that feed later consensus decisions. Keep only explicitly documented, non-consensus liveness exceptions.

### M-6: PoW Cleanup Marker Read Errors Reset Progress and Commit Different Keysets (Medium — New)

**Location:** `x/core/keeper/keeper.go:1995–1999`; caller at `x/core/module/module.go:733–738`.

`CleanupOldCounters` initializes `startHeight = 1` and only changes it when marker Get succeeds with eight bytes:

```1995:1999:blockchain/x/core/keeper/keeper.go
	markerKey := []byte("pow_cleanup_marker")
	startHeight := int64(1)
	if bz, err := store.Get(markerKey); err == nil && len(bz) == 8 {
		startHeight = int64(binary.BigEndian.Uint64(bz))
	}
```

A node-local read error is indistinguishable from a missing marker. That node deletes up to 100 keys starting at height 1 while peers delete from the real cursor. Even if all deleted counters are older than the active PoW window, the committed keysets differ and therefore so do app hashes.

Returning an error from the keeper alone is insufficient: BeginBlock currently logs `CleanupOldCounters` errors and continues.

**Remediation:** Treat marker Get/decode failures as consensus-fatal and propagate the error through BeginBlock. Validate marker length and range before use.

**Tests:** Seed a nontrivial marker, inject a marker Get error and malformed marker, and assert BeginBlock returns an error without deleting any counter.

### M-7: Unbounded Timing and Window Params Can Stall or Corrupt Validated State (Medium — New)

**Location:** validation at `x/core/types/params.go:188–312`; conversions/work at `x/core/keeper/keeper.go:1619–1624`, `1948–1954`, `1982`, `2030–2036`; `x/core/module/module.go:1017`, `3410`, `3480`; `app/ante_metasig.go:960–987`.

Several `uint64` params have no upper bound before conversion or use:

- `PowMessageWindow` is converted to `int64` and drives per-height loops every EndBlock. A large but valid value makes the node scan from height 1 through the current chain tip each block; values above `MaxInt64` also wrap during conversion.
- `SubscriptionPeriod` is converted to `int64`, multiplied by 60, and added to Unix timestamps. Large valid values wrap expiry and can produce missing indexes or unintended paid-tier lifetime.
- `MaxEnvelopeAge` is converted to `time.Duration` and multiplied by `time.Second`. Large valid values wrap duration and can reject otherwise valid relay envelopes or produce invalid nonce expiry.
- `MintInterval` is also converted to `int64`; values above `MaxInt64` change its sign and cadence semantics.

`Params.Validate()` accepts these values. The `PowDifficultyAllowance <= PowMessageWindow*2` validation itself can overflow the unsigned multiplication.

**Impact:** An approved but malformed governance params update can stall EndBlock, disable relay transaction admission, or corrupt subscription timing without being rejected at proposal execution.

**Remediation:** Add explicit domain bounds that make every conversion and loop safe. At minimum:

- cap `PowMessageWindow` to a small operational maximum;
- cap duration params before multiplication/addition;
- use checked arithmetic for timestamp and fee calculations;
- reject values above `math.MaxInt64` before casts;
- avoid overflow in cross-field validation.

**Tests:** Boundary tables at max accepted value and max+1, plus tests proving EndBlock work stays bounded and duration/timestamp arithmetic cannot wrap.

### L-4: Reserve Basis-Point Conversion Still Uses `float64` (Low — Open)

**Location:** `x/core/module/module.go:977`, `3366`.

`uint64(percent * 10000)` truncates binary floating-point values and can under-escrow by one basis point.

**Remediation:** Store reserve percentage as integer basis points or use an explicit fixed-point representation.

### L-5: Relay Registry and Ante Switches Remain Hand-Maintained (Low — Open)

**Location:** `app/relay_messages.go:9–44`, `app/ante_pow.go`, `app/ante_metasig.go`, `app/relay_messages_test.go:12–33`.

All 25 current relay types are covered and both ante switches fail closed on unknown types. The test only pins registry-to-router parity, not registry-to-both-switch parity. A future envelope-bearing message omitted from the registry would route through standard ante.

**Remediation:** Generate dispatch from the registry or make tests execute every registry prototype through both decorators. Assert every envelope-bearing core message is registered or explicitly governance-only.

### L-7: Stale PoW Commentary and Unused `PowDecorator.MinFee` (Low — Open)

**Location:** `app/ante_pow.go:42–46`, `228–229`, `1435`; construction at `app/ante_relay_chain.go:62–64`.

The runtime always validates a non-empty recent block hash, while comments imply CheckTx may skip it. `MinFee` is never read. Empty `LastBlockId` still bypasses membership checks during the bootstrap window.

**Remediation:** Correct comments, remove the unused field, and explicitly bound any empty-hash bootstrap behavior by height.

### L-8: Mutual-Exclusion List Cleanup Discards Delete Errors (Low — New)

**Location:** `x/core/module/module.go:2454`, `2563`, `2835`.

Blocking a user ignores `RemoveFollowedUser`; wildcard topic blocking/following ignores matching list removals. The primary add can then succeed.

**Impact:** A node-local delete failure can commit both mutually exclusive entries on one node while peers commit only one.

**Remediation:** Propagate every cleanup delete error so the transaction cache rolls back.

**Tests:** Inject delete failures for user and wildcard-topic mutual exclusion and assert transaction rejection.

---

### L-9: Valid Zero-Valued Params Cannot Be Applied Through Governance (Low — New)

**Location:** `x/core/module/module.go:1229–1323`.

`applyParamUpdates` uses nonzero values as field presence. Valid values such as `MintDynamicSplit = 0`, `PowCalmPeriodDefinition = 0`, `PowDifficultyAllowance = 0`, `SubscriptionPeriod = 0`, `SubscriptionReservePercent = 0`, and relay fee values of zero silently mean “leave unchanged.” The handler still validates and returns success.

**Impact:** Governance can approve a semantically valid update that succeeds on-chain without applying the requested value. This also makes the documented one-time subscription mode unreachable through the normal params message.

**Remediation:** Use protobuf optional fields or an explicit field mask. Reject an update with no selected fields.

**Tests:** Apply every valid zero-valued field and assert it changes; assert an empty update is rejected.

---

### L-10: Admin Gas Waiver Treats All Deduction Errors as Insufficient Balance (Low — New)

**Location:** `x/core/module/module.go:306–315`.

For level-100+ profiles, any `DeductFeeFromOwner` error is logged as insufficient balance and ignored. That includes a node-local bank/store failure, not only insufficient funds.

**Impact:** One node can skip the deduction while peers deduct and burn, creating asymmetric bank/module state. The liveness policy is documented, but the error classification is too broad.

**Remediation:** Skip only a positively identified insufficient-funds error. Propagate storage and invariant failures.

---

### L-11: Store/v2 Pruning Logs and Suppresses Per-Store Failures (Low — Patch)

**Location:** `patches/cosmos-sdk-store-v2/rootmulti/store.go:698–708`, `721–740`.

Non-`ErrVersionDoesNotExist` IAVL prune failures are logged and ignored, as are earliest-version and commit-info persistence failures.

**Impact:** This is primarily an operational/query-history risk rather than current app-hash risk, but it can leave one node with internally inconsistent prune metadata and data retention.

**Remediation:** Return per-store prune failures to the pruning manager. Keep commit-info cleanup best-effort only if metrics/alerts make repeated failure visible.

## Historical Upgrade and Test Posture

All 44 handlers were reviewed. Several old handlers contain error-discard patterns, notably v1.17.0 subscription-index deletion at `app/upgrades.go:1601–1610`. Those upgrades have already executed on live chains; changing old handler bodies now does not remediate committed state and adds risk without a scheduled replay path.

The useful fix is prospective:

1. Add execution tests for stateful handlers, prioritizing v1.31.0 bridge cleanup, v1.17.0 subscription reindex, and v1.16.0 list migration.
2. Require future migrations to propagate every iterator/write error and include post-migration invariants.
3. Make handler-registration tests exhaustive instead of sampling roughly half the 44 names.

No persisted partial-migration finding is recorded: an upgrade block that returns an error does not commit its cached writes, so a retry starts from the pre-block committed state.

## Urgency Assessment

No finding warrants an emergency release.

**M-6 should be fixed in the next normal release.** It extends the exact node-local read fail-open class already treated as consensus-fatal elsewhere, and the code change is small.

**M-7 should be fixed before any governance proposal changes timing, PoW-window, or subscription params.** Current defaults are safe; the risk is latent in proposal validation.

**M-1 through M-5 should be handled as one consensus-write hardening batch.** They share the same store-failure contract and benefit from one injected-failure test harness.

The highest-value operational prevention remains separating public query load from validator processes. That status was not rechecked because production hosts were not contacted.
