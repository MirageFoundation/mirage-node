Full source-code security review of the `blockchain/` project covering 117 tracked Go/proto/module files. Reviewed transaction admission, relay and standard SDK ante routing, core message handlers, keeper state transitions, genesis and upgrade handlers, bridge attestation logic, orchestrator Solana watcher/minter flows, patched IAVL behavior, and security-relevant tests.

**Ship blockers:** None for current non-bridge operation. Before any bridge/orchestrator re-enable, fix H-2 and review all bridge findings as release blockers. Before scheduling an upgrade that calls `MigrateBridgeMintAttestors`, fix H-1.

## Findings

### H-1: Bridge Mint Attestor Migration Uses Nondeterministic Map Tie-Breaking (High)

**Location:** `x/core/keeper/keeper.go` lines 2408–2457 (`MigrateBridgeMintAttestors`), called by upgrade handlers in `app/upgrades.go`.

The migration iterates `attestation.Attestors`, a Go map, to compute `bestValoper`:

```go
for valoperAddr, power := range attestation.Attestors {
    if power <= 0 {
        continue
    }
    sumPower += power
    if power > bestPower {
        bestPower = power
        bestValoper = valoperAddr
    }
}
```

If a legacy confirmed mint attestation has two or more attestors tied for highest power and `ConfirmedBy` is empty, the selected `bestValoper` depends on Go map iteration order. Different validators can choose different `ConfirmedBy` values during the same upgrade handler, creating a deterministic-state risk at upgrade height.

**Impact:** Potential consensus divergence during the migration if equal-power legacy attestors exist.

**Remediation:** Collect tied max-power valoper addresses, sort them lexicographically, and select the first. Add a migration unit test with two equal-power attestors.

### H-2: Orchestrator Advances `lastSeq` Before Mirage Records Mint Confirmation (High, Bridge Disabled)

**Location:** `orchestrator/attestor/attestor.go` lines 274–289 and 376–389.

After a Solana mint succeeds, the orchestrator updates local `lastSeq` before submitting `MsgBridgeAttestMinted` back to Mirage:

```go
if sig != "" {
    a.lastSeqMu.Lock()
    if burn.Sequence > a.lastSeq[burn.DestinationChain] {
        a.lastSeq[burn.DestinationChain] = burn.Sequence
    }
    a.lastSeqMu.Unlock()

    if err := a.retry(ctx, func() error {
        return a.mirage.SubmitBridgeMinted(ctx, burn.BurnID, burn.DestinationChain, sig, burn.TxHash)
    }); err != nil {
        a.logger.Printf("WARN failed to submit bridge minted burn_id=%s: %v", burn.BurnID, err)
    }
}
```

If `ExecuteMint` succeeds but `SubmitBridgeMinted` fails after retries, the local sequence cursor advances anyway. The orchestrator can later reject or skip lower/equal sequence burns as stale even though Mirage never recorded the mint confirmation.

**Impact:** When the bridge is re-enabled, a transient Mirage submission failure can leave Solana minted while Mirage lacks the corresponding minted record, requiring manual reconciliation or another validator to recover.

**Current mitigating condition:** `cmd/orchestrator/main.go` hard-panics with `ORCHESTRATOR_HARD_DISABLED`, so this is not live in current production operation.

**Remediation:** Advance `lastSeq` only after Mirage acknowledgment, or persist separate states for “external mint succeeded” and “Mirage confirmed.” Add a background reconciler for externally minted but unacknowledged burns.

### M-1: `GetParams` Still Falls Back to Defaults on Corrupt or Invalid Params (Medium, Accepted Risk Regression Surface)

**Location:** `x/core/keeper/keeper.go` lines 1074–1092.

`GetParams` returns `types.DefaultParams()` when stored params fail unmarshal or validation:

```go
if err := k.cdc.Unmarshal(bz, &p); err != nil {
    ctx.Logger().Error("core/GetParams: corrupted params in store; using defaults", "err", err)
    return types.DefaultParams()
}
if err := p.Validate(); err != nil {
    ctx.Logger().Error("core/GetParams: invalid params in store; using defaults", "err", err)
    return types.DefaultParams()
}
```

This was documented as accepted risk in the March retest. It remains the largest deliberate exception to the project’s fail-fast policy: corrupt or invalid on-chain params silently switch execution to defaults rather than halting.

**Impact:** Bad upgrade writes, disk corruption, or unexpected params encoding can change economics and bridge thresholds without governance intent.

**Remediation:** If availability no longer outweighs correctness, split this into strict execution reads and genesis/init defaults. Execution paths should return an error on corrupt or invalid params.

### M-2: Solana Watcher Cold Start Can Replay Full Program History (Medium, Bridge Disabled)

**Location:** `orchestrator/chains/solana/watcher.go` lines 218–286 and 377–409.

When `.resume_state` is missing, `loadState` returns nil and leaves `lastSig` empty. `pollBurns` then paginates signatures until it reaches the end of program history, collecting every page before processing oldest to newest.

**Impact:** A fresh deploy, lost state directory, or misconfigured state path can cause a large historical scan, RPC load spike, queue storm, and duplicate attest attempts. On-chain bridge attestation logic is mostly idempotent, but the operational blast radius is high.

**Current mitigating condition:** The orchestrator is hard-disabled.

**Remediation:** Require an explicit bootstrap cursor, cap first-sync history by default, or make full-history replay an operator-confirmed mode.

### M-3: `retry` Treats Permanent Errors as Success (Medium, Bridge Disabled)

**Location:** `orchestrator/attestor/attestor.go` lines 404–437.

`retry` returns nil for permanent errors:

```go
if isPermanentError(err) {
    a.logger.Printf("INFO  permanent error (no retry): %v", err)
    return nil
}
```

Callers cannot distinguish success from “skipped because permanent.” For mint and attestation paths this can suppress higher-level error logging and make dropped work look successful.

**Impact:** Reduced operator visibility during bridge recovery or replay.

**Remediation:** Return a sentinel error such as `ErrSkippedPermanent` and let callers log and account for skipped burns separately from successful work.

### M-4: Paid Relay Fee Paths Can Succeed Without Charging Protocol Fee (Medium)

**Location:** `x/core/module/module.go` lines 298–337.

Two fee paths intentionally return success without charging:

- Admin users (`level >= 100`) skip deduction if `DeductFeeFromOwner` fails.
- Paid non-admin users return nil when their profile is missing or cannot unmarshal.

The admin path is explicitly documented in comments as a product choice. The missing-profile path is less clearly intentional and can allow a user with paid level metadata but missing/corrupt profile state to submit relay operations without the protocol fee.

**Impact:** Economic fairness and supply-accounting drift in inconsistent state.

**Remediation:** Keep the admin waiver only if explicitly accepted. For non-admin paid levels, fail closed when the profile is missing or corrupt.

### M-5: Mint Distribution Mints Full Supply Before Best-Effort Validator Sends (Medium)

**Location:** `x/core/keeper/keeper.go` lines 1386–1422.

`MintIfNeeded` mints the full interval amount to the module account, then logs and continues if validator account sends fail:

```go
if err := k.bank.MintCoins(ctx, types.ModuleName, coins); err != nil {
    return err
}
// ...
if err := k.bank.SendCoinsFromModuleToAccount(ctx, types.ModuleName, accAddr, val_coins); err != nil {
    ctx.Logger().Error("mint distribution: failed to send to validator", ...)
    failedValopers = append(failedValopers, r.validator.OperatorAddress)
    continue
}
```

The March retest accepted continuation to avoid halting minting, but failed distributions leave newly minted tokens in the core module account rather than distributing, burning, or explicitly escrowing them.

**Impact:** Supply increases while intended recipients do not receive all rewards; module balance can accumulate undistributed mint.

**Remediation:** Choose an explicit policy: abort on any distribution failure, burn undistributed remainder, or record escrowed undistributed rewards with a recovery path.

### M-6: Outbound Bridge Mint Attestation Trusts First `destination_tx` (Medium, Bridge Disabled)

**Location:** `x/core/module/bridge_handlers.go` lines 472–518 and 579–604.

The first `destination_tx` stored for a burn becomes canonical. Later validators can provide a different destination tx; the handler logs the mismatch but continues using the original canonical tx.

This protects state consistency, but the chain does not verify that `destination_tx` is a finalized Solana transaction that paid the burn recipient. Correctness depends on validator/orchestrator verification before signing `MsgBridgeAttestMinted`.

**Impact:** If a compromised or buggy orchestrator writes the first bogus `destination_tx`, honest validators can still add power to the canonical record unless their off-chain verification rejects it.

**Remediation:** Document the validator trust boundary clearly before bridge re-enable. Prefer validator-side verification of recipient, amount, burn id, and finalized Solana signature before submitting `MsgBridgeAttestMinted`; long term, consider light-client or fraud-proof verification.

### M-7: Solana Destination Address Validation Does Not Decode Public Keys (Medium, Bridge Disabled)

**Location:** `x/core/types/bridge.go` lines 391–416.

`ValidateBridgeDestinationAddress` checks length and base58 alphabet for Solana addresses but does not decode the address into a 32-byte Solana public key.

**Impact:** Some invalid but plausible-looking strings can pass chain validation and fail later in the Solana mint path.

**Remediation:** Use Solana public key decoding for `chainID == "solana"` and reject values that do not decode to a valid 32-byte public key.

### M-8: Relay Message Allowlist Is Spread Across Multiple Switches (Medium)

**Location:** `app/app.go` lines 137–155, `app/ante_metasig.go` lines 793–825 and 964–967, `app/ante_pow.go`.

Relay routing depends on `isRelayMessage`; signature verification and PoW enforcement are maintained in separate type switches. `RelaySigDecorator` still has `default: // ignore others`, and `MsgSetLevel` appears in `RelaySigDecorator` even though it is not relay-routed by `isRelayMessage`.

The current live allowlist is safe because mixed relay/non-relay transactions are rejected. The risk is regression: a future core message added to one switch but not the others can revive the old class of signature or PoW coverage bugs for that message.

**Remediation:** Use a single shared relay message registry or add a test that enforces parity between relay routing, relay signature verification, and PoW handling.

### L-1: Standard Ante Handler Construction Error Is Ignored (Low)

**Location:** `app/app.go` lines 261–269.

`stdAnte, _ := authante.NewAnteHandler(stdOpts)` ignores construction errors. This is unlikely with the current static options, but a future SDK or wiring change could leave `stdAnte` invalid and fail later at runtime.

**Remediation:** Check the error and panic during app initialization if standard ante construction fails.

### L-2: `ProcessProposal` Performs Minimal Validation Only (Low)

**Location:** `app/app.go` lines 339–352.

`ProcessProposal` decodes each transaction and rejects only empty message lists. It does not run ante-level validation.

**Impact:** Malicious proposers can include transactions that decode but will fail during block execution, wasting block space. This is not a signer bypass because normal execution still applies ante checks.

**Remediation:** Consider running lightweight structural validation or ante simulation if proposer DoS becomes a concern.

Delegation, undelegation, and redelegation are covered, but `MsgCancelUnbondingDelegation` is not explicitly rejected. SDK signer checks still apply, and the chain’s self-delegation-only model limits impact.

**Remediation:** Add `MsgCancelUnbondingDelegation` to the decorator and extend the staking disable test.

Profile pagination skips rows that fail JSON unmarshal and ignores errors from all list loaders. Clients can see incomplete profile data instead of an explicit query error.

## Remediation Applied (Same-Day Follow-up)

Same-session remediation landed after the review above. Bridge and orchestrator findings were intentionally left untouched per standing policy (bridge dormant). The following non-bridge items were addressed, plus a cross-cutting "never halt the chain" refactor that was adopted as a project invariant for the BeginBlock/EndBlock surface.

### Chain-wide never-halt invariant

BeginBlock, EndBlock, and every helper they call MUST NEVER return a non-nil error or panic. A non-nil return halts the chain on every honest validator; a panic in ABCI paths crashes the node. All internal failures are logged loudly and the block proceeds with the safest possible fallback. The error-return signatures on these functions are retained for API compatibility only and are always nil.

Sites converted to log-and-continue in this pass:

- `MintIfNeeded` — entire function; every error path replaced.
- `BeginBlock` — `BurnAllFromModuleName(fee_collector)`, `MintIfNeeded`, `SetCurrentDifficulty(base)` (first-boot init), `CleanupOldCounters` (100-block sweep).
- `EndBlock` — `SetCurrentDifficulty` (busy increase and calm decrease) and `SetConsecutiveLowUsage` (calm increment).
- `GetParams` — corrupt-bytes and Validate-failure branches no longer panic.

### B) Upgrade verification hardening (`verify_upgrade.py`)

Post-upgrade verification failed on some local/container layouts because node logs
were assumed at a single path. The verifier now resolves logs across supported
layouts and accepts an explicit override.

- `scripts/verify_upgrade.py`:
  - added `resolve_node_log_dir()` with support for:
    - `NODE_LOG_DIR` override
    - `NODE_HOME/logs/node`, `NODE_HOME/logs`
    - `~/.mirage/node/logs/node`, `~/.mirage/logs/node`
    - `/root/.mirage/node/logs/node`, `/root/.mirage/logs/node`
  - both `check_upgrade_handler_ran()` and
    `check_never_halt_invariant()` now use this resolver.

Result: section 3/4 upgrade checks no longer fail due to path-only assumptions.
