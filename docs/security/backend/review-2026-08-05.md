## Executive Summary

First full audit of the Mirage backend: a Flask application with no sessions and no cookies, in which a client's identity is a secp256k1 keypair, writes are authenticated by a signature over canonical bytes ("envelopes"), and reads generally pass a `mirage1…` address as a query parameter. The backend holds the validator key and the rewards-pool key, brokers every user write to the chain, and owns an operational database (`mirage_backend`) alongside read-only access to the indexer's (`mirage_indexer`).

The cryptographic core of the design is good. Canonical byte encoding is domain-separated and length-prefixed with explicit field tags, so the signature-reuse and field-confusion classes are structurally closed (`shared/canon.py`). Envelope replay protection for the backend's own signed endpoints is a correct nonce-plus-timestamp construction backed by a real `UNIQUE(owner, action, nonce)` constraint. Error handling is centralized and never leaks exception text. There is no `eval`, `exec`, `pickle`, `os.system`, `shell=True`, or unsafe `yaml.load` anywhere in the backend, indexer, or shared code, and essentially all SQL is parameterized — the f-string SQL that exists interpolates placeholder counts and server-side config fragments, never request data. The existing `tests/cases/test_backend_security.py` (970 lines) genuinely tests cross-user authorization, signature replay, and PoW-proof reuse.

**The defining weakness is not cryptographic. It is that authorization is inconsistent, and the inconsistency is invisible.** The codebase contains a correct, complete signed-admin primitive — `_verify_admin_stats_request` (`routes/public.py:7977`) verifies a signature, derives the address from the pubkey, checks the address matches, guards the nonce, and only then checks `level >= 100`. It is used by three stats endpoints. Four *other* administrative endpoints — `/api/get_reports`, `/api/core/resolve_report`, `/api/admin/rewards/suspend`, `/api/admin/rewards/unsuspend` — determine administrative authority by reading an address **string from the request** and looking up its level. On-chain addresses are public, so anyone who knows a moderator's address can read every moderation report, delete reports, and suspend or unsuspend any user's rewards. The right pattern and the wrong pattern live in the same three files. See **H-1**.

The same shape recurs in the payout path, and there it costs money. `/api/rewards/claim` takes `owner` from the JSON body with no signature, then executes `SELECT unclaimed → send tokens → UPDATE claimed_at` across three separate autocommit connections with no lock, no `SELECT … FOR UPDATE`, no unique constraint, and no idempotency key. Two concurrent requests both read the same unclaimed rows and both pay out. The edge allows 50 requests per second per IP, which is roughly two orders of magnitude more concurrency than the attack needs. See **C-2**.

Beyond authorization, the review found that user-scoped read endpoints treat the `address` query parameter as identity, so one request retrieves another user's inbox, invite codes, referral history, balance and reserve, taste preferences, and block lists (**H-2**); that a `_is_localhost()` helper trusts `X-Forwarded-For` — which `AGENTS.md` explicitly forbids — and behind the reverse proxy evaluates to true for every request, which both weakens the debug-endpoint gate to `BACKEND_DEBUG` alone and silently switches production quest assignment from deterministic to random rolls (**M-1**); and that ten known dependency advisories are outstanding, seven of them in `flask-cors`, in the two packages that are the only ones pinned with exact `==` (**M-5**).

Two structural observations frame the rest. First, because `/chain/rest/*` and `/chain/rpc/*` are publicly proxied, **every backend-side check on a chain write is advisory** — an attacker simply posts to the chain directly. (At the reviewed baseline the outer transaction was also unsigned, which made this free; since v1.32.0 an attacker must sign the outer transaction and fund their own gas, but the conclusion is unchanged, because the chain ante — not the backend — is what actually rejects a bad write.) This is a defensible architecture, but 22 endpoints wrap their PoW precheck in `except Exception: pass`, and 16 skip backend signature verification while 13 perform it, so no reader can tell which checks are load-bearing (**H-3**). Second, the backend has no way to detect wrong data in the indexer DB, and the indexer enforces delete and edit authorization that the chain deliberately does not (**M-8**).

**Ship blockers:** **C-1** and **C-2**. C-1 permits unauthorized spending from any funded account and is reachable from the internet; C-2 permits repeated payouts from the rewards pool. Both were exploitable as the code stood at the baseline, with no configuration precondition. **C-1 is remediated in v1.32.0; C-2 is still open.** See the Remediation Status table below.

## Findings

### C-1: Relay Transactions Deduct an Attacker-Chosen Fee From an Attacker-Chosen `fee.payer` With No Authorization — Any Account's Balance Can Be Drained Through the Public Chain Endpoint (Critical)

> **Remediated in v1.32.0.** Local reproduction (`scripts/reproduce_c1_fee_drain.py`) drained 500 MIRAGE before the fix. After ante rewire + validator outer signing, the same attack is rejected at CheckTx and the victim balance is unchanged. Regression: `tests/test_blockchain.py --category c1_gas_payer`.

**Location:** `blockchain/app/ante_metasig.go` lines 1004–1104 (`RelayGasFeeDecorator`), the relay ante chain at `blockchain/app/app.go` lines 355–366, the router at `blockchain/app/app.go` lines 168–224, public exposure at `deploy/templates/caddy/Caddyfile` lines 121–145, and the backend's unsigned tx construction at `web/backend/tx.py` lines 75 and 92. *All references are to the reviewed baseline (`3ccf8c70`); `RelayGasFeeDecorator` and the placeholder signature no longer exist. The relay chain now lives in `blockchain/app/ante_relay_chain.go`.*

Mirage relay messages do not use standard Cosmos signature verification. The backend builds the outer transaction with a placeholder signature and lets the chain verify the inner envelope instead:

```75:92:web/backend/tx.py
    fee.payer = require_runtime().validator_payer_addr
...
    return TxRaw(body_bytes=body_bytes, auth_info_bytes=auth_bytes, signatures=[b"\x00"]).SerializeToString()
```

That is intentional, and the relay ante chain is built accordingly. It contains no `SigVerificationDecorator`, no `SetPubKeyDecorator`, no sequence check, and no `DeductFeeDecorator`:

```355:366:blockchain/app/app.go
			relayAnte := sdk.ChainAnteDecorators(
				setup,
				validateBasic,
				govDec,
				timeout,
				gasSize,
				logDec,
				meta,
				powDec,
				ensure,
				metaFees,
			)
```

`metaFees` is `RelayGasFeeDecorator`, which replaces the SDK's `DeductFeeDecorator`. It resolves the payer directly from the transaction's `fee.payer` field and transfers the transaction's own declared fee out of that account:

```1086:1096:blockchain/app/ante_metasig.go
		fees := ftx.GetFee()
		if !fees.IsZero() {
			addr, err := sdk.AccAddressFromBech32(payer)
			if err != nil {
				ctx.Logger().Warn("relay invalid fee payer address", "err", err.Error())
				return ctx, fmt.Errorf("invalid fee payer address: %w", err)
			}
			if err := d.BankKeeper.SendCoinsFromAccountToModule(ctx, addr, authtypes.FeeCollectorName, fees); err != nil {
```

**Nothing establishes that the payer authorized this payment.** The SDK normally enforces that invariant in `DeductFeeDecorator`, which requires the fee payer to be a transaction signer or to have granted an explicit `feegrant`. The relay chain runs neither, and `FeegrantKeeper` is `nil`. `authante.NewValidateBasicDecorator()` counts signatures but does not verify them, so a single dummy byte satisfies it, exactly as the backend's own client demonstrates.

**The fee amount is also attacker-controlled, and is bounded below but not above.** The only fee check is a floor:

```1025:1029:blockchain/app/ante_metasig.go
		offered := ftx.GetFee()
		if !offered.IsAnyGTE(required) {
			ctx.Logger().Warn("relay insufficient fee", "offered", offered.String(), "required", required.String(), "min_gas_prices", minPrices.String(), "gas", gas)
			return ctx, fmt.Errorf("insufficient fee: got %s required any >= %s (minGasPrices=%s, gas=%d)", offered, required, minPrices, gas)
		}
```

`required` is `min_gas_price × gas`; `offered` must merely be at least that. The full `offered` amount is then deducted. There is no ceiling, and the `relay_max_gas_fee` parameter (default 500 MIRAGE) that *sounds* like the relevant cap is not consulted here — it is used only in `x/core/module/module.go:290`, inside the message handler, to bound the deduction from the *user's own reserve*. An attacker can therefore declare a modest `gas` (to stay within the block limit) and an arbitrarily large `fee.amount`, and drain the victim's entire balance in a single transaction. In `CheckTx` the decorator even pre-verifies the victim can cover it (lines 1053–1060), so an underfunded target fails admission cleanly and a funded one proceeds.

**Routing does not require the attacker to look like the backend.** `mirageAnteRouter` selects the relay chain purely on message type:

```201:205:blockchain/app/app.go
		if isRelayMessage(m) {
			isRelayTx = true
		} else {
			hasNonRelay = true
		}
```

**And the chain is publicly reachable.** Caddy proxies both chain ports to the internet with only a per-IP rate limit:

```121:145:deploy/templates/caddy/Caddyfile
	# Chain RPC (CometBFT) - includes WebSocket at /chain/rpc/websocket
	handle /chain/rpc/* {
		...
		uri strip_prefix /chain/rpc
		reverse_proxy 127.0.0.1:26657
	}

	# Chain REST (Cosmos SDK)
	handle /chain/rest/* {
		...
		uri strip_prefix /chain/rest
		reverse_proxy 127.0.0.1:1317
	}
```

**The complete attack:** construct any relay message (`MsgVote`, `MsgFollowTopic`, anything in `isRelayMessage`); sign the envelope with your *own* key so `RelaySigDecorator` passes; solve the Argon2id PoW so `PowDecorator` passes, or use a level‑1 account which is PoW-exempt; set `authority` to any valid address; set `signatures` to one dummy byte; set `fee.payer` to the victim and `fee.amount` to the victim's balance; POST to `/chain/rest/cosmos/tx/v1beta1/txs`. The victim's balance moves to the fee collector. The attacker spends only PoW. Every validator's fee account, the rewards pool, and every ordinary user is a target, and the victim's balance is public information.

**Impact:** Unauthorized spending from arbitrary accounts by an unauthenticated internet attacker. Direct, permanent loss of user and treasury funds. This also makes every rate limit and validation in the backend irrelevant to an attacker who has read `tx.py`.

**Remediation:**

1. **Restore fee-payer authorization in `RelayGasFeeDecorator`.** The relay design's own premise is that the envelope signer is the authenticated party, so the fee must come from an account the envelope authorizes — in practice the envelope-derived user, or the relaying validator identified by a mechanism that cannot be forged. Do not accept a `fee.payer` that no one signed for. The minimal correct change is to ignore `ftx.FeePayer()` entirely on the relay path and derive the payer from the verified envelope.

   *As implemented (v1.32.0):* a different and stronger route was taken. `RelayGasFeeDecorator` was retired in favour of the SDK's own `SigVerificationDecorator` followed by `DeductFeeDecorator`, and the backend now signs the outer transaction with the validator key using unordered transactions (so validators still never track sequence numbers). `fee.payer` is therefore honoured only when its owner has signed the `SignDoc`, which is checked cryptographically rather than inferred from the envelope.

2. ~~**Add an upper bound on the deducted fee** and enforce `relay_max_gas_fee` (or a dedicated ante-level cap) so no single relay transaction can move an unbounded amount into the fee collector, independent of who pays.~~

   **Withdrawn — this recommendation was wrong, and implementing it caused a functional regression.** A ceiling of `min(gas × relay_min_gas_price, relay_max_gas_fee)` crosses the CheckTx minimum-gas-price floor at `relay_max_gas_fee / min_gas_price` gas — 500,000 gas at the deployed values. Above that crossing the fee a node is *required* to offer exceeds the fee the chain will *accept*, so no valid transaction exists at all. Measured effect: posts over 10,727 characters (inside the 20,000-character paid-tier limit) and every bulk operation, including bulk follows at ~2.3M gas, became unsubmittable. The premise was mistaken: once item 1 is in place the payer has signed the `SignDoc`, which covers `auth_info` — the fee amount, gas, and payer — so the payer has consented to the exact amount. C-1 was an authorization defect, not a magnitude defect, and stock Cosmos has no maximum fee for exactly this reason. The bound was removed and the reasoning recorded on `relayAnteDecorators` in `blockchain/app/ante_relay_chain.go` so it is not reintroduced. `relay_max_gas_fee` remains correct in its original role, bounding the deduction from a paid user's own reserve in `x/core/module`.

   Two review-process notes, since both are reusable. First, the Go unit test written to cover this bound asserted a 500M fee at 1,000,000 gas was acceptable — but passed zero `minPrices`, so the floor never ran. Floor and ceiling were never exercised together, which is precisely why the crossing was not caught. Second, `content_limits.sub_over_20000_rejected` went **green for the wrong reason**: it posts 20,050 characters and expects failure, and got one from "fee too high" rather than from the content-length rule, while the neighbouring acceptance case used only 1,050 characters and never reached the crossing. A rejection test needs an acceptance test immediately beneath the limit to bracket it, or it silently certifies a broken path.

3. **Reject non-empty/non-placeholder `fee.payer` on relay transactions** as a defense-in-depth assertion, so a malformed or malicious payer field fails closed rather than being honored. *Superseded by item 1 as implemented:* a `fee.payer` that no one signed for is now rejected by signature verification, which is a stronger check than a shape assertion. Covered by `c1.empty_fee_payer_foreign_pubkey_rejected`.
4. **Add a regression test asserting a relay tx naming a third-party `fee.payer` is rejected.** *Done*, in `tests/cases/test_blockchain_chain_rules.py::test_c1_unauthorized_gas_payer`: an unsigned third-party payer, an empty `fee.payer` with a foreign pubkey, and a forged 64-byte signature against a funded victim (the sharpest case, since it passes `SetPubKey` and only signature verification can stop it) are each asserted rejected, plus an assertion that the victim's balance is unchanged. The companion "fee above the cap" test was replaced by `c1.high_gas_relay_accepted`, which submits at double the withdrawn cap and requires acceptance through delivery — the inverse property, guarding item 2's regression.
5. **Reconsider exposing `/chain/rest/*` and `/chain/rpc/*` to the internet.** Broadcast endpoints in particular give attackers a path that bypasses every backend control. If public read access is required, expose queries and withhold `broadcast_tx`. **Still open** — no decision recorded. Note that this is now the load-bearing reason H-3's conclusion survives the C-1 fix.
6. Audit historical fee-collector inflows for transactions whose `fee.payer` is not the relaying validator, to determine whether this has been exploited. **Still open.**

### C-2: `/api/rewards/claim` Is Unauthenticated and Pays Before It Marks Claimed, With No Lock or Idempotency Key — Concurrent Requests Pay Repeatedly From the Rewards Pool (Critical)

**Location:** `web/backend/routes/quests.py` lines 775–812, `web/backend/reward_distributor.py` lines 337–533, `web/backend/db.py` lines 31–35 and 489–505.

The endpoint takes the beneficiary from the request body and never proves the caller controls it:

```790:795:web/backend/routes/quests.py
        data = request.get_json(force=True) or {}
        owner = str(data.get("owner", "")).strip().lower()

        if not owner:
            return jsonify({"error": "owner required"}), 400
```

There is no signature, no envelope, and no nonce — in contrast to `/api/seen_posts`, `/api/mark_inbox_viewed`, and `/api/referrals/precheck_opt_in` in the same codebase, which all sign a payload of the form `action:{addr}:{ts}:{nonce}`.

`claim_rewards` then performs a read-modify-write across three *separate* connections, each in autocommit mode, with the payout in the middle. Step one reads the unclaimed rows with a bare `SELECT` — no `FOR UPDATE`:

```357:365:web/backend/reward_distributor.py
                cur.execute(
                    """
                    SELECT id, reward_type, reward_data, reason
                    FROM pending_rewards
                    WHERE LOWER(owner) = LOWER(%s) AND claimed_at IS NULL
                    """,
                    (owner,),
                )
```

Step two sends the tokens on-chain:

```433:434:web/backend/reward_distributor.py
        if mirage_rewards and payout_amount > 0:
            send_result = self.send_reward(owner, payout_amount, f"quest_rewards:{len(mirage_rewards)}_quests")
```

Step three, on a third connection, finally marks the rows claimed:

```504:511:web/backend/reward_distributor.py
                        cur.execute(
                            """
                            UPDATE pending_rewards
                            SET claimed_at = %s, payout_amount = %s
                            WHERE id = %s
                            """,
                            (ts, reward_payout, reward["id"]),
                        )
```

Every mechanism that would make this safe is absent. Both connection helpers are autocommit, so no transaction spans the sequence:

```31:35:web/backend/db.py
def connect_backend_db() -> psycopg.Connection:
    """Open a read-write connection to the backend-owned PostgreSQL database."""
    cfg = get_config()
    url = cfg.get_backend_db_url()
    return psycopg.connect(url, autocommit=True)
```

`pending_rewards` has only ordinary indexes — no unique constraint that a second claim would violate (`db.py:489–505`). There is no idempotency key and no tx hash recorded before payment.

**Two exploit paths, both reachable:**

- **Concurrency.** Fire N simultaneous `POST /api/rewards/claim` for the same `owner`. All N read the same unclaimed rows, all N call `send_reward`, all N mark claimed. The user receives N times their entitlement. The Caddy `api_limit` zone permits 50 requests per second per IP, and the race window spans a `miraged tx bank send` subprocess with a 30-second timeout — an enormous window. Because the endpoint is unauthenticated, an attacker can also spread the requests across IPs.
- **Retry.** If `send_reward` succeeds but the process dies, is killed by the 120-second gunicorn timeout, or errors before step three, the rows remain unclaimed and the next claim pays again.

The same window also over-issues invite codes: `_generate_unique_invite_codes` inserts new codes (`reward_distributor.py:477–489`) before the rows are marked claimed.

**Impact:** Unbounded drain of the rewards pool by any user, and by any third party on any user's behalf, limited only by the pool balance (checked at `reward_distributor.py:299–307`, itself racy). `QUESTS_PAYOUTS_ENABLED` gates whether transfers are real; where it is true, this is direct loss.

**Remediation:**

1. **Make the claim atomic and make it the payment authorization.** Claim the rows *first* with a conditional update that can only succeed once, inside an explicit transaction, and pay only for rows the update actually returned:
   `UPDATE pending_rewards SET claimed_at = %s WHERE owner = %s AND claimed_at IS NULL RETURNING id, reward_type, reward_data`. If it returns no rows, another request already claimed them. This inverts the current order so a crash can only ever under-pay, which is recoverable, rather than over-pay, which is not.
2. **Require a signature.** Reuse the existing `action:{addr}:{ts}:{nonce}` pattern and `_guard_push_request`, so only the key holder can trigger their own claim and each claim carries a single-use nonce.
3. **Add an idempotency key** persisted before the transfer, so a retry after an ambiguous CLI outcome is detectably a duplicate.
4. **Stop using autocommit for multi-statement money operations.** Open one transaction for the whole claim.
5. **Add a regression test** that issues concurrent claims and asserts exactly one payout, and a test that simulates a crash between payout and mark-claimed.

### H-1: Four Administrative Endpoints Derive Authority From a Client-Supplied Address String, While the Correct Signed-Admin Primitive Exists in the Same Codebase (High)

**Location:** `web/backend/routes/public.py` lines 6390–6406 (`/api/get_reports`), `web/backend/routes/core.py` lines 3134–3155 (`/api/core/resolve_report`), `web/backend/routes/quests.py` lines 856–888 (`/api/admin/rewards/suspend`) and 936–961 (`/api/admin/rewards/unsuspend`). Correct pattern for contrast: `web/backend/routes/public.py` lines 7977–8026.

The codebase already contains a complete and correct signed-admin check. `_verify_admin_stats_request` decodes the pubkey, derives the address from it, rejects a mismatched `address` field, verifies the signature over `stats:{addr}:{ts}:{nonce}`, runs the nonce/timestamp replay guard, and only then checks the level:

```8014:8025:web/backend/routes/public.py
    signed_payload = f"{STATS_ADMIN_ACTION}:{user_addr.lower()}:{timestamp}:{nonce}"
    if not _verify_signature(pub_dec, sig_dec, signed_payload.encode("utf-8")):
        return None, (jsonify({"error": "invalid signature"}), 400)

    ok, gerr = _guard_push_request(user_addr, STATS_ADMIN_ACTION, timestamp, nonce)
    if not ok:
        return None, (gerr[0], gerr[1])

    if get_user_level(user_addr) < STATS_ADMIN_MIN_LEVEL:
        return None, (jsonify({"error": "forbidden"}), 403)
```

Four other administrative endpoints do none of that. They read an address *string* out of the request and look up its level. `/api/core/resolve_report` is representative:


**Mirage addresses are public on-chain data.** A moderator's address is discoverable from any post, vote, or profile they have ever touched, and `/api/get_users` enumerates profiles. ### H-2: User-Scoped Read Endpoints Treat the `address` Parameter as Identity — Reclassified (v1.33.0)

**Original finding** treated every address-keyed read as a confidentiality leak. That overstated the risk for data that is already chain-public.

**What is actually public (deliberate):**

- `get_preferences`, `get_blocked_users`, `get_user_blocked` — read through `connect_db`, the indexer DB. Anyone with a public node can recompute the same lists from chain state.
- `get_inbox` — reply content is on chain. Gating the convenience endpoint while the same data is queryable from any node is theater, and would invite the harder audit question of what the gate is controlling.
- `referrals/precheck` — pre-signup; takes a username, no identity exists yet. The original test failure was a false positive.
- `rewards/summary`, `rewards/achievements`, `referrals/summary` — backend-owned but not credentials and not actions. Left public as a **deliberate disclosure** so admin suspension-status call sites keep working without a new endpoint.

**What was a real credential leak:**

- Unused invite codes in `invite_codes` are bearer credentials. Rather than authenticate that read while the feature is unused, `REGISTRATION_INVITE_CODE_REQUIRED` is now authoritative: when false (fleet-wide), `get_invite_codes` and `validate_invite_code` return 404 and bootstrap omits the `invite_codes` section. When true, `get_invite_codes` requires a signed read and `validate_invite_code` must not return `owner`.

**Writes are not reads.** `/api/rewards/claim` is authenticated (C-2) because the multiplier is applied at claim time — a stranger can destroy up to 80% of pending reward value without taking custody. That is why claim is gated and `get_inbox` is not.

**Status:** Reclassified. Rationale recorded in `tests/cases/test_backend_authz.py` `ROUTE_POLICY` and in `docs/guides/api_request_signing.md`.

### H-3: The Backend Is Not an Enforcement Boundary for Chain Writes, but Parts of It Are Written as Though It Were — and 22 PoW Prechecks Are Silently Skipped on Error (High)

> **Partially addressed after v1.32.0.** `tx.py:92` no longer builds a placeholder signature — outer relay txs are signed with the validator key — so the "unsigned outer tx" premise below is historical. The conclusion is unchanged: `/chain/rest/*` and `/chain/rpc/*` are still publicly proxied (C-1 item 5, still open), so the chain ante remains the only enforcement boundary and every backend check on a chain write is still advisory. The 22 swallowed prechecks, the 13-vs-16 verification split, and the undocumented trust model are all unchanged.

**Location:** `web/backend/tx.py` line 92 (at the reviewed baseline; now a real signature); the 22 `except Exception: pass` PoW precheck blocks in `web/backend/routes/core.py` (including lines 819–820, 1394–1395, 1496–1497, 1640–1641, 1766–1767, 1891–1892, 1984–1985, 2077–2078, 2201–2202, 2295–2296, 2408–2409, 2523–2524, 2620–2621, 2710–2711, 2829–2830, 2973–2974, 3073–3074, 3312–3313, 3831–3832, 4070–4072, 4287–4288); the ownership precheck at lines 3281–3283; `deploy/templates/caddy/Caddyfile` lines 121–145.

Because the chain's REST and RPC ports are publicly proxied (see C-1), any attacker can construct and broadcast a relay transaction without touching the backend. **The chain's ante handlers are the only real enforcement point, and always have been.** At the reviewed baseline the outer transaction also carried a placeholder signature, so this cost the attacker nothing but PoW; since v1.32.0 they must sign the outer transaction and fund their own gas, which raises the price of the bypass without changing where enforcement lives. That is a legitimate architecture. The problem is that the code does not say so, and behaves inconsistently in ways that make the security model unreadable.

**Backend signature verification is applied to 13 endpoints and omitted on 16.** `set_username`, `set_biography`, `edit`, `annotate`, `post`, `send_tokens`, `subscribe`, `set_auto_renewal`, `award`, both push-token endpoints, and `report` verify the envelope before relaying; `vote` verifies it only for non-subscribers (`core.py:4086` versus `4122`). The 16 block/follow/agent/delete endpoints do not. Where verification *does* run, this review confirmed that the canonical bytes cover every payload field forwarded to the chain — including `media` arrays, `tag`, `override`, `appendix`, `amount`, `level`, and `direction` — with `authority` correctly and deliberately excluded and always set from `require_runtime().validator_payer_addr`. So there is no field-substitution gap. The gap is that a reader cannot tell whether the 16 omissions are considered safe by design or are oversights.

**The PoW precheck is unenforceable by construction.** On 22 endpoints it is wrapped so that any failure — a malformed field, an Argon2 error, a canonical-bytes exception — silently skips the check:

```1394:1395:web/backend/routes/core.py
            except Exception:
                pass
```

An adjacent authorization precheck is explicitly documented as advisory, which is the honest version of the same idea:

```3281:3283:web/backend/routes/core.py
        except Exception:
            pass  # If DB check fails, let chain proceed
```

**Envelope timestamp windows are enforced on 2 of 27 chain relays.** `_validate_envelope_timestamp` (90 seconds, `core.py:391–397`) is called only from `set_username` (699–706) and `post` (3657–3660). Worse, two endpoints *invent* a timestamp when the client omits one, which would silently break signature verification if it were ever added:

```2580:2580:web/backend/routes/core.py
        timestamp = int(data.get("timestamp", 0)) or int(time.time() * 1000)
```

**Impact:** No direct exploit beyond C-1 — the chain rejects what the backend lets through. The cost is that the backend's checks provide no assurance while appearing to, which is how C-1 survived: a reader tracing `authority` and `fee.payer` through `tx.py` would reasonably assume the outer transaction was signed. (Since v1.32.0 it is. The hazard the finding describes is the mismatch between apparent and actual enforcement, and that mismatch is what allowed a one-byte placeholder to sit on the fee path unnoticed.) Inconsistent, silently-skipped validation is also the condition under which a future change that *does* make the backend load-bearing will be unsafe by default.

**Remediation:**

1. **Write down the trust model** in a module docstring in `routes/core.py` and in `docs/architecture/`: the chain ante is authoritative; backend checks are UX fast-fail only; `/chain/*` is a supported bypass. Then make the code consistent with it.
2. **Decide on the prechecks and apply the decision uniformly.** Either verify signature and PoW on all 29 endpoints or none. Half is the worst option because it implies coverage that does not exist.
3. **Stop swallowing precheck exceptions.** A precheck that cannot run should reject with a clear error, not silently pass. If a fast-fail check erroring is genuinely acceptable, log it at `Warn` with a distinguishable tag so the rate is observable.
4. **Require an explicit `timestamp`** on every relay endpoint and apply `_validate_envelope_timestamp` uniformly. Never synthesize a timestamp the user did not sign.
5. **Reconsider public `/chain/*` broadcast exposure** (also C-1 remediation 5). Withholding `broadcast_tx` at the edge would make the backend an actual boundary and give these checks real value.

### M-1: `_is_localhost()` Trusts `X-Forwarded-For` and Evaluates True for Every Request Behind the Reverse Proxy — It Gates Both the Debug Endpoints and Production Quest Determinism (Medium)

**Location:** `web/backend/routes/quests.py` lines 1016–1032, used at lines 478, 1040, 1142, 1234, 1277.


Second, and active right now, the same helper selects production quest-assignment behavior:

```478:478:web/backend/routes/quests.py

```

### M-3: Invite Codes Use a Non-Cryptographic RNG, Are Enumerable Through an Unauthenticated Oracle That Returns the Owner, and Generation Reads the Entire Table (Medium)

**Location:** `web/backend/reward_distributor.py` lines 51–95, `web/backend/routes/public.py` lines 9812–9848.

```55:59:web/backend/reward_distributor.py
def _generate_invite_code() -> str:
    """Generate a random invite code in format XXXX-XXXX."""
    part1 = "".join(random.choices(INVITE_CODE_CHARS, k=4))
    part2 = "".join(random.choices(INVITE_CODE_CHARS, k=4))
    return f"{part1}-{part2}"
```

Three issues compound.

**`random.choices` is the Mersenne Twister, not a CSPRNG.** Invite codes gate registration when `REGISTRATION_INVITE_CODE_REQUIRED` is set and carry a reward entitlement, so they are security-relevant values and belong to `secrets`. MT state is recoverable from enough observed output; an attacker who collects codes could in principle predict future ones. The keyspace itself is 32⁸ ≈ 2⁴⁰, adequate only if guessing is rate-limited.

**Guessing is barely rate-limited, and success is confirmed with the owner's identity.** `/api/validate_invite_code` has no per-endpoint limit beyond the shared 50 req/s per-IP `api_limit` zone, and returns the code owner on success (`public.py:9847–9848`). That is both a brute-force oracle and an identity leak. Combined with **H-2**, an attacker who can already list a victim's codes does not even need to guess.

**Generation loads the whole table into memory on every claim:**

```69:70:web/backend/reward_distributor.py
            cur.execute("SELECT code FROM invite_codes")
            existing = {row[0] for row in cur.fetchall()}
```

This runs inside the claim path (C-2), so it grows linearly with all codes ever issued. Uniqueness is enforced in Python against that snapshot; the real guarantee is the `code VARCHAR(9) PRIMARY KEY` (`db.py:75`), which means a concurrent duplicate surfaces as an unhandled `IntegrityError` mid-claim rather than a retry.

**Impact:** Registration gating and reward entitlements resting on guessable, enumerable tokens; an unauthenticated mapping from code to owner address; and a per-claim full-table scan on the money path.

**Remediation:** Switch to `secrets.choice` and widen to at least 10 characters (2⁵⁰). Drop `owner` from the `validate_invite_code` response — the client needs validity, not identity. Add a strict per-IP and per-code-prefix limit on validation attempts, and count failures. Replace the read-all-then-check pattern with `INSERT … ON CONFLICT (code) DO NOTHING RETURNING code` in a bounded retry loop, so the primary key is the sole arbiter and no table scan occurs.

### M-7: Analytics Permanently Links a Pseudonymous Browsing Identity to a `mirage1` Address, With No Retention Bound (Medium)

**Location:** `web/backend/stats.py` lines 205–221 and 257–265, `web/backend/routes/public.py` lines 8131–8148.

The visitor identifier and the account address are stored together, and the binding is upserted so it survives:

```205:211:web/backend/stats.py
            cur.execute(
                """
                INSERT INTO stats_events (created_at, event_type, visitor_hash, address, path)
                VALUES (%s, %s, %s, %s, %s)
                """,
                (now_ts, event_type, visitor_hash, address, path[:200]),
```

```215:221:web/backend/stats.py
                    INSERT INTO stats_visitors (visitor_hash, address, platform, first_seen_at, last_seen_at)
                    VALUES (%s, %s, %s, %s, %s)
                    ON CONFLICT (visitor_hash) DO UPDATE SET
                        last_seen_at = EXCLUDED.last_seen_at,
                        platform = COALESCE(stats_visitors.platform, EXCLUDED.platform),
                        address = COALESCE(EXCLUDED.address, stats_visitors.address)
```

The hygiene here is genuinely good and should be acknowledged: raw IPs are never stored by this module, the raw visitor id is salt-hashed before any write (`stats.py:119–120`), the User-Agent is reduced to a platform enum rather than stored verbatim (`stats.py:134–141`), and the visitor and IP hashes are domain-separated so they cannot collide (`client_ip.py:75–86`).

The problem is the join, not the hashing. `visitor_hash` is a stable per-device key present on pre-login requests; `address` is attached as soon as any request carries `?address=`. Once both appear, the row permanently associates everything that device browsed with that account. `stats_events` records the API path per event, so the record includes which profiles were viewed — the code even takes care to null the address for `/api/get_profile` paths (`stats.py:318`), showing the sensitivity was recognized in aggregate reporting but not in storage. Neither table has a TTL or cleanup job, in contrast to `push_event_seen` (7 days) and `push_nonces`, which do.

Two amplifiers: **H-2** means an attacker can attach *any* address to their own requests, poisoning the mapping; and `/api/stats/visitor_attribution` accepts an arbitrary `visitor_id` from anyone with no authentication (`public.py:8131–8148`), so third parties can write rows.

**Impact:** A permanent deanonymization dataset on a platform whose premise is pseudonymity. Any backend DB compromise, careless admin export, subpoena, or `/api/admin/stats/export` misuse links wallets to browsing history. The data's existence, not its confidentiality, is the exposure.

**Remediation:** Decide the minimum needed for product analytics and store only that. Concretely: stop writing `address` and `visitor_hash` on the same row — keep aggregate counters keyed on one or the other; add a retention job dropping `stats_events` beyond 30–90 days and clearing `stats_visitors.address` on the same schedule; rotate the visitor salt periodically so linkage cannot extend indefinitely; and document the retention policy where users can see it. Require identity proof (or drop `address`) on `visitor_attribution`.

### M-8: The Backend Cannot Detect Wrong Data in the Indexer DB, and the Indexer Enforces Authorization the Chain Deliberately Does Not (Medium)

**Location:** `web/backend/db.py` lines 21–28, `indexer/chain_client.py` lines 30–33 and 122, `indexer/message_processor.py` lines 776–780 and 1493–1573, `indexer/address_utils.py` lines 83–108, `indexer/database.py` lines 31–33, `indexer/main.py` lines 517–548 and 609–612.

The backend reads all chain state — profiles, balances, levels, params, difficulty, block hashes, supply, validators — from `mirage_indexer` over a read-only role, with no gRPC path of its own. The read-only separation is correctly implemented (`get_indexer_ro_url()`, `GRANT SELECT` in `deploy/entrypoint.sh:328–331`). What does not exist is any verification: no block-hash reconciliation, no Merkle proof, no second source, no drift detector. **Whatever the indexer writes, the backend serves as chain truth**, including the `profiles.level` values that four admin gates depend on (H-1) and `get_user_level` uses everywhere. The indexer in turn trusts a local CometBFT RPC and a plaintext gRPC channel (`grpc.insecure_channel`) without validating that blocks are canonical.

Two indexer-side issues have direct backend consequences:

**Authorization for deletes and edits lives only in the indexer.** This is deliberate and documented on the chain side (`blockchain/x/core/module/module.go:2937–2943`: "Authorization is enforced by the INDEXER"), and the indexer does implement it:

```776:780:indexer/message_processor.py
        # Enforce ownership: only the original owner can edit (admins cannot)
        db_owner = self.db.get_post_owner(override)
        if not db_owner or db_owner.lower() != (owner or "").lower():
            logger.warning("Rejected edit %s: owner mismatch", tx_hash)
            return
```

The consequence is that content integrity has no on-chain backstop: a chain transaction that edits or deletes another user's post *succeeds* on-chain, and only the indexer's check keeps it from taking effect. Admin delete rights are evaluated against the possibly-stale `profiles.level` in the indexer DB (`message_processor.py:1526–1527`), not live chain state. Separately, `derive_owner_from_dict` prefers an unauthenticated `owner` field over the envelope-derived address (`address_utils.py:92–106`), which is not currently exploitable because `MsgDelete` has no `owner` field, but is the wrong precedence order to leave in an identity function.

**Failures advance the height pointer.** Handlers catch exceptions, log, and return; the block still completes and `set_last_height` moves on (`main.py:609–612`), so a transient error permanently drops a message with no gap detector and no replay. Writes are autocommit with no per-block transaction (`database.py:31–33`), so a crash mid-block can leave vote side effects (`user_topic_stats`, `preferences`) applied without the corresponding `votes` row, and a replay re-applies them. A fresh or long-stopped indexer silently starts at most `INDEXER_MAX_LOOKBACK_DAYS` (default 7) back (`main.py:517–548`), so older history is simply absent.

**Impact:** The indexer is a single point of failure for moderation correctness and for the level values backing administrative authorization. Silent divergence between chain state and served state is undetectable by design, and several failure modes produce it without an error.

**Remediation:** Add a drift detector that periodically re-queries a sample of profiles, balances, and levels over gRPC and alerts on mismatch — it will not close the trust gap, but it converts silent divergence into a signal. Read `level` for authorization decisions from the chain rather than the indexer DB, or at minimum stamp indexer level rows with the height at which they were observed and reject stale ones. Wrap block processing in a single transaction and make handler failure fatal to the block so the height pointer cannot advance past dropped data; add a gap detector comparing `last_height` to chain head. Change `derive_owner_from_dict` to prefer the envelope. Track the lookback truncation explicitly so incomplete history is visible rather than assumed.

### L-1: `stream_proxy` Follows Redirects, Reflects Third-Party Content With `Access-Control-Allow-Origin: *`, and Length-Checks the UID Without Charset-Checking It (Low)

**Location:** `web/backend/routes/public.py` lines 8231–8300.

The proxy host is hardcoded, which correctly prevents arbitrary-host SSRF:

```8246:8259:web/backend/routes/public.py
        if not video_uid or len(video_uid) < 10 or len(video_uid) > 100:
            return jsonify({"error": "invalid video uid"}), 400
...
                target_url = f"https://videodelivery.net/{video_uid}/manifest/{path}"
```

Three residual issues. `video_uid` is validated only by length, not character set, and `path` is a `<path:path>` converter that accepts slashes, so `requests` will normalize `../` segments and reach unintended paths on `videodelivery.net`. The client query string is appended wholesale (8264–8267). And `requests.get(target_url, headers=headers, timeout=30, stream=True)` leaves `allow_redirects` at its default `True`, so a redirect from the upstream host is followed to any destination and its body returned to the caller — the one path by which this becomes a genuine SSRF pivot. Responses are returned with `Access-Control-Allow-Origin: *`, making the node a CORS-stripping proxy for that host.

**Remediation:** Constrain `video_uid` with `re.fullmatch(r"[0-9a-f]{10,100}", …)`, reject `..` in `path`, pass `allow_redirects=False`, and forward only an allowlisted set of query parameters.

### L-4: Validator and Rewards-Pool Keys Use the Plaintext `test` Keyring, Read by the Backend Process (Low)

**Location:** `deploy/templates/node/client.toml` (`n = "test"`), `deploy/deploy.sh` (`--n test`), `web/backend/reward_distributor.py` line 104, `web/backend/node.py` lines 33 and 205–260.

Production uses the Cosmos `test` keyring backend, which stores keys unencrypted on disk. The backend shells out to `miraged keys list/show` at startup to resolve the validator address and pubkey, and `reward_distributor` hardcodes `KEYRING_BACKEND = "test"` to spend from `rewards_pool`. Any file-read primitive or code execution in the backend container therefore yields both the validator key and the rewards-pool key.

**Remediation:** Separate the rewards-pool signer from the web process — a small local signing service, or a queue the web process writes and a separate worker signs. ### I-1: 95 Bare `except Exception` Blocks in the Two Route Modules (Informational)

`routes/core.py` has 56 and `routes/public.py` 39. Many are legitimate 400-mapping wrappers around signature parsing that fail closed. But the same construct is used for the 22 PoW prechecks that fail *open* (H-3), the middleware that hides inbox errors (H-2), and the fail-soft paths in `chain.py` (M-6). Because the pattern is uniform, a reader cannot distinguish fail-closed from fail-open without tracing each one, and neither can a reviewer of a future diff.

**Suggestion:** Adopt a convention that a bare `except Exception` must either re-raise, return an error, or carry a one-line comment stating why continuing is safe — the `# If DB check fails, let chain proceed` comment at `core.py:3283` is the model.

## Positive Security Controls Observed

- **Canonical byte encoding is structurally sound.** `shared/canon.py` prefixes every message with `b"mirage.core.v1:" + MsgName + b"\x00"`, writes fields in ascending tag order, and length-prefixes every string and byte field. Domain separation plus unambiguous framing closes the signature-reuse and field-confusion classes by construction rather than by validation. Verified against the tag ordering the Go side expects, including the `envelope_pow` tag-5 placement.
- **Where backend signature verification runs, the signed bytes cover every forwarded field.** Traced all 13 verifying endpoints: `media` arrays, `tag`, `override`, `appendix`, `amount`, `level`, `direction`, and `agents` lists are all inside the canonical bytes. `authority` is excluded deliberately and is always set from `require_runtime().validator_payer_addr`, never from user input — the project rule holds across all 29 endpoints.
- **Identity is derived from the pubkey, not accepted from the request, on every signed write.** `derive_address_from_pubkey` establishes the actor, and where an `address` field is also present it must match (`public.py:8012–8013`). This is why the write path has no impersonation finding despite H-2's read-path failures.
- **`_verify_admin_stats_request` is a complete, correct authorization primitive** — signature, pubkey-derived address, address/pubkey match, nonce replay guard, then level check, in that order. H-1 is entirely about extending its use, not about designing it.
- **Envelope replay protection is real and backed by a constraint.** `_guard_push_request` enforces a 5-minute window and inserts into `push_nonces` with `ON CONFLICT DO NOTHING RETURNING`, and the table genuinely declares `UNIQUE(owner, action, nonce)` (`db.py:373–381`) plus a `CHECK (owner = LOWER(owner))`. The guard fails closed to 503 on DB error. This was verified specifically because the pattern is silently useless without the constraint.
- **Error handling never leaks internals.** `error_utils.py` is a single registry of ~180 code/message pairs; `safe_error` logs the traceback with a correlation id and returns only `internal server error` plus that id. `get_error_code` raises on an unmapped message, so drift fails loudly at development time.
- **SQL is parameterized throughout.** Every f-string SQL construction found in `web/backend/`, `shared/`, and `indexer/` interpolates either a generated `%s` placeholder list or a server-side config fragment (`_deleted_filter()` from `IGNORE_DELETIONS`). User-supplied `sort`/`by` values are whitelisted in Python against a fixed tuple and never reach `ORDER BY` (`public.py:5470–5473`). No injection was found in ~32,000 lines of reviewed Python, including the indexer paths that store attacker-supplied on-chain content.
- **No dangerous execution primitives anywhere.** No `eval`, `exec`, `pickle`, `os.system`, `os.popen`, `shell=True`, or unsafe `yaml.load` in `web/backend/`, `shared/`, or `indexer/`. The two `subprocess` users pass argv lists.
- **The existing security test suite is substantive.** `tests/cases/test_backend_security.py` (970 lines) covers signature replay with substituted content, PoW proof reuse across messages, cross-user delete/edit of posts and comments, foreign username and account deletion, self-award and award replay, push-token registration with an invalid signature, foreign unregister, and address/pubkey mismatch. This is real adversarial testing, not smoke testing.
- **Client IP handling follows the project rule.** `get_trusted_client_ip()` uses `CF-Connecting-IP` then `remote_addr`, never `X-Forwarded-For`; IPv6 is bucketed to /64; IP and visitor hashes are domain-separated with distinct prefixes. M-1 is a violation of this rule *elsewhere*, which the existence of this correct helper makes easy to fix.
- **Media validation sniffs magic bytes rather than trusting the client.** `validate_upload` ignores the declared content type and filename, requires the detected kind to match the requested kind, and the local provider generates paths from `uuid4().hex` with a `realpath` containment check plus a regex guard on delete. Caddy serves `/media/*` with `X-Content-Type-Options: nosniff` and `Content-Disposition: inline`.
- **Read-only database separation is correctly implemented and actually used.** The backend's indexer connection resolves through `get_indexer_ro_url()`, and the role is granted `SELECT` only in `deploy/entrypoint.sh`. Backend-owned writes go to a separate database.
- **`params.py` fails hard**, raising on any missing required chain parameter rather than defaulting — the behavior M-6 asks `chain.py` to adopt.
- **Push delivery is owner-scoped and multiply throttled**: 5 pushes per 30 minutes per user, a 10-mention cap per post, one trending push per user per 24 hours, and 7-day dedup retention.
- **The bridge removal was thorough.** `routes/bridge.py` is gone, and `mirageAnteRouter` explicitly rejects all five bridge message types (`app.go:186–191`), closing the previous review's H-2 at the code level rather than by params. The only residue is two now-unused Python dependencies (M-5).

## Prioritized Recommendations

1. ~~**Fix the fee-payer authorization hole (C-1).**~~ **Done in v1.32.0** by requiring a real outer signature from the gas payer rather than deriving the payer from the envelope. The "upper bound on the deducted fee" half of this recommendation was **withdrawn as incorrect** — see C-1 item 2. What remains from C-1: decide whether public `/chain/*` broadcast should exist at all (item 5), and audit historical fee-collector inflows (item 6). With C-1 closed, **C-2 is now the most severe open finding in this document.**
2. **Make the reward claim atomic and authenticated (C-2).** Claim rows first with `UPDATE … WHERE claimed_at IS NULL RETURNING`, pay only for returned rows, wrap it in one transaction, and require the signed `action:{addr}:{ts}:{nonce}` proof. Then audit historical payouts against `pending_rewards` for duplicates.
3. **Extend the existing signed-admin primitive to all four unprotected admin endpoints (H-1)** and delete `_require_admin()`. This is a small, mechanical change against a helper that already exists and is already correct — the highest ratio of risk removed to code changed in this review.
4. **Require identity proof on user-private reads (H-2)**, split `/api/bootstrap` accordingly, and remove the unauthenticated write from `get_inbox` and the address-keyed writes in `factory.py` middleware.
5. **Write down the trust model and make the code consistent with it (H-3).** State that the chain ante is authoritative and backend checks are advisory, then stop swallowing precheck exceptions and apply the timestamp window uniformly. Without this, future changes will keep assuming a boundary that is not there — which is how C-1 went unnoticed.
6. **Delete `_is_localhost()` and unregister the debug endpoints in production (M-1)**, and fix the production quest-roll determinism regression at `quests.py:478`.
7. **Fail hard on missing `CLIENT_HASH_SALT` (M-2)** and remove the per-process generation fallback.
8. **Upgrade `flask-cors` and replace `CORS(app)` with an origin allowlist together (M-5, L-2)**, bump `flask`, drop the dead `pynacl` and `base58`, and add `pip-audit` to CI.
