**Scope:** `web/backend/` — all 33 tracked Python files (~25,110 lines), all 87 registered HTTP routes, quest/reward accounting, transaction construction, media providers, push delivery, analytics, database access, and the backend-facing `shared/` modules. `indexer/` and `deploy/` were inspected only where they define a backend trust or configuration boundary.
**Out of scope:** `web/frontend/`, blockchain consensus internals (audited separately in [`../blockchain/review-2026-08-06.md`](../blockchain/review-2026-08-06.md)), external storage-provider implementations, and production servers.

**Previous review:** [`review-2026-08-06.md`](review-2026-08-06.md), with the Aug 5 review and authoritative retest linked from there. This is a new full audit, not a diff review or remediation retest.

## Executive Summary

The backend's main security boundaries remain intact. The validator fee payer is still cryptographically bound by a real outer SignDoc signature; signed admin routes derive identity from the public key; `X-Forwarded-For` is not trusted; indexer outages fail as 503 instead of returning plausible data; and concurrent reward claims remain serialized. No new Critical or High finding was found.

Two new Medium findings are both in the quest subsystem:

1. **The action-side `QuestTracker` ignores the required runtime quest configuration.** It imports a second, hardcoded settings module where quests and achievements are always enabled and invite probabilities are 30%. The deploy template says quests are disabled and both invite probabilities are zero, but every successful post/vote still enters this tracker. That can create quest state and pending rewards while the operator believes the system is off. See **M-1**.
2. **Daily quest assignment is check-then-insert without serialization.** Concurrent first requests can each choose a different set and leave one user with more than `QUESTS_DAILY_COUNT` completable quests. Both independent assignment implementations have the same shape. See **M-2**.

The most concrete non-quest addition is an admin-triggered SSRF gap: validator monikers beginning with `http://` or `https://` bypass the private-IP checks applied to peer IPs, then receive a server-side POST from the stats fan-out path (**L-1**). The endpoint is admin-gated and the path is fixed, so this is Low rather than a general public SSRF.

The Aug 6 reward residuals remain: a crash after successful payout broadcast but before DB commit can double-pay (**L-2**), and non-JSON CLI output with exit code zero is treated as success (**L-3**). Push notifications have a similar delivery-order problem: events are permanently deduplicated before daemon-thread delivery completes (**L-4**).

The selected local security suite printed **99/99 passed**, but `stats.pure` was skipped because required env was unavailable to the host process. `_skip()` sets `passed=True`, and the final summary counts it as a pass. The actual result was **98 executed passes, one skip, zero failures**. This is the same “green but not looking” failure mode that previously hid C-2 and M-3; see **L-6**.

**Current ship blockers:** None. The deploy template has both `QUESTS_ENABLED=false` and `QUESTS_PAYOUTS_ENABLED=false`, so M-1/M-2 do not justify an out-of-band release. **They are blockers for enabling quests or payouts** and should be fixed before any such rollout. No production server was contacted to verify runtime overrides.

## Findings

### M-1: Action-Side Quest Tracker Ignores Required Runtime Flags (Medium)

**Location:** `web/backend/quest_tracker.py` lines 24, 251–258, 277–305, and 1014–1029; `web/backend/quest_settings.py` lines 3–23; call path `web/backend/routes/core.py` lines 159–183 and 4107–4109 / 4337–4338. Contrasting runtime configuration: `web/backend/settings.py:49–56`, `routes/quests.py:63–72`, and `deploy/templates/env/backend.env:60–86`.

`routes/quests.py` correctly reads required env values and returns a disabled summary when `QUESTS_ENABLED=false`. `QuestTracker`, used after successful post and vote submissions, does not import those settings. It imports `quest_settings.py`, where:

- `QUESTS_ENABLED = True`
- `ACHIEVEMENTS_ENABLED = True`
- invite-recruit and invite-earner chances are both `0.30`
- daily/flash counts and intervals are separate hardcoded copies

The deploy template currently sets `QUESTS_ENABLED=false`, both invite probabilities to `0`, and payouts to false. Despite that, `_track_quest_progress()` constructs the hardcoded tracker and calls `update_progress()` after successful user actions. The tracker can assign quests, advance them, and insert `pending_rewards`. An assigned `invite_recruit` can also activate the 10,000 MIRAGE referral reward path when a referred user sets a username.

**Impact:** Operator controls do not control the full subsystem. Quest liabilities and referral rewards can accrue while the UI and summary endpoint report quests disabled. If payouts are later enabled without cleaning or validating those rows, historical unintended rewards become claimable. This is an economic-integrity and configuration-authority failure, not a direct unauthenticated theft path.

**Remediation:** Delete the duplicate runtime constants in `quest_settings.py`. Put every quest flag/count/chance in one required-env settings module and have both route and tracker paths import it. Gate `_track_quest_progress()` before constructing the tracker. Fail startup if values are missing or outside valid ranges.

**Regression tests:**

- `QUESTS_ENABLED=false` plus successful post/vote → no `user_daily_quests`, `user_flash_quests`, achievements, or `pending_rewards` writes.
- Invite chances `0` → neither invite special quest can be assigned through either path.
- Route summary and action tracking must observe the same counts/chances.

### M-2: Concurrent Daily Assignment Can Exceed the Configured Quest Count (Medium)

**Location:** `web/backend/routes/quests.py` lines 315–421; duplicate path `web/backend/quest_tracker.py` lines 269–329; schema `web/backend/db.py:395–404`.

Both implementations:

1. Query whether the user has any daily quests.
2. Return only if rows already exist.
3. Select up to `QUESTS_DAILY_COUNT` random quests outside a lock.
4. Insert each selected quest with `ON CONFLICT (owner, day_utc, quest_id) DO NOTHING`.

The primary key prevents duplicate *quest IDs*. It does not enforce a maximum number of quest IDs for a user/day. Two concurrent first requests can both observe zero rows, choose partially disjoint sets, and commit their union. With a configured count of two, the user can receive three or four completable quests.

The route path is reachable through public `GET /api/rewards/summary?owner=…` and `/api/bootstrap?address=…` when quests are enabled. The tracker path can race on concurrent successful actions even while the route feature is disabled because of M-1.

**Impact:** A user can obtain and complete more paid quests than configured. The additional rewards have distinct quest reasons and are not removed by the pending-reward uniqueness control.

**Remediation:** Consolidate assignment into one function. Start a real transaction, acquire a per-owner/day PostgreSQL advisory transaction lock, re-read the assigned count while holding it, and insert only the remaining number of slots before commit. No schema change is required.

**Regression test:** Start at least four parallel first-summary/first-action calls for a fresh owner and assert the committed row count is exactly `QUESTS_DAILY_COUNT`, then repeat across several random selections.

### L-1: Stats Fan-Out Accepts Arbitrary HTTP(S) Validator Monikers (Low)

**Location:** `web/backend/stats.py` lines 796–824 and 949–989; `web/backend/routes/public.py` lines 8110–8169.

`_normalize_moniker_url()` returns any string beginning with `http://` or `https://` unchanged. The hostname validation and raw-IP rejection below that branch never run. `discover_servers()` consumes validator and peer monikers from indexer-backed network state; the signed admin aggregate route then POSTs the admin proof to `<moniker>/api/admin/stats/export`.

The peer-IP fallback correctly requires `ipaddress.ip_address(ip).is_global`, but a moniker such as `http://127.0.0.1:…` or `http://169.254.169.254` bypasses that control.

**Impact:** A malicious/misconfigured validator moniker can cause an admin-triggered server-side request to loopback, private, or link-local addresses and receive the signed stats proof. The requested path is fixed and the trigger requires a valid admin request, which limits severity.

**Remediation:** Parse every moniker with `urllib.parse.urlsplit`; allow only HTTP(S), reject credentials/fragments, resolve the hostname, and reject every non-global IP result. Prefer an explicit fleet-domain allowlist if validator web endpoints are known operationally. Apply the same validator to already-schemed and inferred-HTTPS monikers.

**Regression tests:** Reject schemed loopback/private/link-local/IPv6 monikers, credentials, and DNS names resolving to private addresses; keep known public domains accepted.

### L-2: Reward Claim Still Pays Before Marking Claimed (Low — Carryover)

**Location:** `web/backend/reward_distributor.py` lines 478–581.

The advisory lock correctly closes concurrent double-pay. It does not survive a worker kill after a successful `miraged tx` broadcast but before `claimed_at` is committed. A retry then sees the rows as unclaimed and pays again. Invite codes are generated through separate autocommit connections inside the same claim, so they can also survive a claim rollback.

**Impact:** Rewards-pool over-pay or duplicate invite issuance during a narrow process-crash/deploy window. No request directly forces the crash.

**Remediation:** Reserve rows first with `UPDATE … WHERE claimed_at IS NULL RETURNING …`, commit the reservation, and make payout recovery explicitly idempotent. Move invite-code insertion into the same claim transaction or give it an idempotency key tied to the pending reward.

### L-3: Payout CLI Treats Ambiguous Success Output as a Transfer (Low — Carryover)

**Location:** `web/backend/reward_distributor.py` lines 216–236.

After exit code zero, missing `code` defaults to zero; malformed JSON falls through to a heuristic txhash scrape and finally `return True, None, None`.

**Impact:** Rewards can be marked claimed without a verified txhash or unambiguous accepted broadcast.

**Remediation:** Fail closed unless parsed JSON contains a non-empty txhash and integer `code == 0`. Replace the CLI path with Cosmos tx REST using `BROADCAST_MODE_SYNC`, matching the main backend transaction architecture.

### L-4: Push Events Are Deduplicated Before Delivery Completes (Low)

**Location:** `web/backend/push_events.py` lines 23–44; `web/backend/push_listener.py` lines 247–265, 307–318, 505–515, and 570–603; `shared/push.py` lines 510–548.

The listener inserts `push_event_seen` before calling `send_push_for_*`. Those helpers launch daemon threads and return before Expo delivery is known. The listener then advances its cursor. A process exit, missing context, Expo failure, or thread exception after the insert leaves the event permanently seen and the cursor past it.

**Impact:** At-most-once behavior where durable retry is expected; users silently miss notifications. The seven-day dedup cleanup does not help because the source cursor does not rewind.

**Remediation:** Use a small durable outbox state machine (`pending` → `sent`) or mark the event complete only after a successful Expo ticket is stored. Keep an attempt count and bounded retry deadline; do not use detached daemon threads as the durability boundary.

**Regression test:** Crash/fail after reservation but before send, restart the listener, and assert the event is retried exactly once to completion.

### L-5: Flash Quest Cap Check and Insert Are Not Atomic (Low)

**Location:** `web/backend/routes/quests.py` lines 142–200; tracker equivalent `web/backend/quest_tracker.py:400–478`; schema `web/backend/db.py:425–442`.

The route path counts active flash quests, checks the next-eligible timestamp, then inserts and updates the timestamp using separate connections. Concurrent requests can both pass the count/cooldown checks. The `(owner, starts_at)` key only resolves races that land in the same second; requests spanning a second boundary can create more than the configured active count.

**Impact:** Extra completable flash quests and rewards under narrow concurrent timing.

**Remediation:** Serialize flash assignment with the same per-owner advisory lock proposed for M-2 and perform count/cooldown/insert/update in one transaction.

### L-6: Test Skips Are Reported as Passes (Low — Assurance)

**Location:** `tests/common.py` lines 119–125 and 1029–1044.

`_skip()` creates `TestResult(passed=True)`. The final summary counts only `passed`, `failed`, and total; it does not report skipped tests separately or fail security categories that did not execute.

This review's command printed `RESULT: 99/99 passed, ALL OK` while the output contained:

> `SKIP stats.pure — backend modules not importable: CLIENT_HASH_SALT is required…`

The factual result was 98 executed passes, one skip, zero failures.

**Impact:** A required security control can go dormant while CI/operator output remains fully green, repeating the failure mode that previously hid the reward race and invite-script RNG gap.

**Remediation:** Give `TestResult` an explicit status, report pass/fail/skip counts separately, and make skips fail in security/release-gate categories unless individually allowlisted with a documented reason.

### L-7: Arbitrary Address Query Parameters Mutate Last-Seen State (Low)

**Location:** `web/backend/factory.py` lines 98–112; `web/backend/user_last_seen.py` lines 19–47; analytics identity extraction `web/backend/stats.py:111–128`.

Every `/api/*` request treats `?address=` or `?admin_address=` as the acting user for last-seen tracking without verifying a signature. Any client can keep any known address active by polling once per minute. The same unverified address is associated with analytics visitor identity on most routes.

**Impact:** DAU/MAU, retention, welcome stats, and campaign attribution can be poisoned; pseudonymous visitor IDs can be deliberately linked to third-party addresses. It does not grant account capabilities.

**Remediation:** Update `user_last_seen` only from derived/verified identity (`derive_address_from_pubkey` and signed-read helpers). For public browsing, track the salted visitor only and do not bind an address supplied solely by query string.

### L-8: Invite Main-Site Gate Trusts the Client Host Header (Low — Latent)

**Location:** `web/backend/routes/public.py` lines 9792–9795 and 9884–9900.

When invite registration is enabled, `_is_main_site()` decides whether validation is allowed using `request.host`, which is client-controlled unless an upstream virtual-host policy guarantees otherwise.

**Impact:** A caller reaching another deployment while supplying `Host: mirage.talk` can bypass the intended deployment restriction. The feature is currently disabled by template, and the endpoint no longer reveals code owners.

**Remediation:** Gate on required server-side deployment configuration, not the request Host header. Add a spoofed-Host test on a non-main-site configuration.

### I-1: Unsigned / Bad-Proof Reward Claim Grace Remains Open Until 2026-10-05 (Informational — Accepted)

**Location:** `web/backend/settings.py` lines 97–116; `web/backend/routes/quests.py` lines 809–833.

Until the cutoff, anyone can trigger a pending reward claim for any owner. The payout goes to that owner, not the caller, and concurrent double-pay is closed.

**Remediation:** Do not extend the cutoff without a new product decision. On or immediately after 2026-10-05 UTC, verify unsigned and unverifiable proofs return 401 in the deployed configuration.

### I-2: Security-Relevant Soft Defaults Remain (Informational — Carryover)

**Location:** `web/backend/settings.py:58–63`; `shared/config.py:176–177`.

Media uploads and indexer enablement still default true if unset, unlike required boolean settings.

**Remediation:** Require explicit values at startup, especially for public media upload enablement.

### I-3: Large Route Modules and Broad Exception Surfaces Remain (Informational — Carryover)

`routes/public.py` remains roughly 9.9k lines and `routes/core.py` roughly 5.1k. Broad exception handling and duplicate quest implementations make security review and invariant enforcement harder. This is directly implicated in M-1/M-2: two independent assignment paths drifted in both configuration source and concurrency behavior.

**Remediation:** When next touching quests, consolidate quest assignment first. Do not perform a general route-module refactor solely for this finding.

## Positive Security Controls Observed

- **C-1 remains closed.** Relay transactions carry one real 64-byte outer signature, use unordered mode, and bind `fee.payer` to the validator.
- **Admin identity remains signed.** Live probes reject unsigned report, reward-suspension, stats-export, and stats-aggregate requests.
- **Claim concurrency control works.** Four concurrent signed claims produced exactly one payout in the local test.
- **Trusted client IP control holds.** Backend code contains no `X-Forwarded-For` trust path; client hashing fails startup without a valid salt.
- **Indexer failures remain explicit.** Missing/unavailable indexer state maps to 503 rather than plausible defaults.
- **Route inventory is complete at the declared-marker level.** All 87 registered routes are represented; there were no undeclared/stale routes or current policy violations.
- **Upload bounds and content sniffing remain in place.** Global request size and per-kind policy checks survived review.
- **Stream proxy hardening holds.** Path validation, query allowlisting, and `allow_redirects=False` remain.
- **Dependency posture is clean under the documented acceptance.** `pip-audit` found no known vulnerabilities after the two explicitly accepted advisories.
- **Static scan found no High-severity result.** Bandit reported zero Highs; its Medium output was dominated by conservative B608 flags on controlled/static query composition, with no confirmed user-controlled SQL identifier found.

## Prioritized Recommendations

1. **Unify quest configuration and assignment (M-1/M-2/L-5).** One required-env source, one assignment implementation, one per-owner transaction lock.
2. **Add disabled-mode and concurrency regression tests** before enabling quests or payouts.
3. **Make reward payout crash-safe and unambiguous (L-2/L-3).** Reserve idempotently; use Cosmos tx REST sync broadcast; require txhash/code.
4. **Validate every stats moniker URL (L-1)** with DNS/IP checks or a fleet-domain allowlist.
5. **Make push delivery durable (L-4)** using an outbox/pending state rather than pre-send dedup plus daemon threads.
6. **Report skips honestly (L-6)** and fail release-gate security categories when required checks do not execute.
7. **Bind last-seen/address analytics only to verified identity (L-7).**
8. **Replace request-Host invite gating (L-8)** before invite registration is re-enabled.
9. **Let the unsigned claim grace expire on 2026-10-05 (I-1)** and run a deployed post-cutoff smoke check.
10. **Revisit the plaintext `test` keyring** when operationally feasible; it remains the largest accepted backend residual.
