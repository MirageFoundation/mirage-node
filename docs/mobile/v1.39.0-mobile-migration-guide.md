# Mirage v1.39.0 mobile migration guide

This guide matches the chain and backend contracts in v1.39.0. Do not invent fields.

> **Temporary compatibility bridge:** v1.39.0 servers temporarily accept the wire protocol used by the currently published mobile release, including its topic routes, protocol-0 posts, period-less subscriptions, and unsigned content personalization. This is a migration window, not permission for new mobile code to retain topic or Agent contracts. Implement the community contract below; the bridge will be removed after the migrated release is available in both stores, adoption is confirmed, and a cutoff is announced. See `docs/mobile/LEGACY_SHIM.md` for the temporary server behavior and teardown gate.

## Routes and deep links

Replace `/t/:slug` with `/c/:slug`. Replace `/topics` with `/communities`. Do not keep `/t/:slug` or `/topics` as redirects; those paths 404. Show a community as `[test]`, not `#test` or `c/test`. In post bodies, `[test]` links to `/c/test`. `@` stays for users. Remove agents, quests, referrals, and invite-and-earn screens.

Send `X-Mirage-Visitor` on every backend request. Keep a deferred campaign `ref` only until visitor attribution succeeds. Do not call a referral or signup-reward API.

## Posts

`MsgPost` field 101 is `community` (same tag as the old topic string). Field 106 is `protocol_version` and must be `1`. Comments leave community empty and inherit the parent. Root posts accept any valid lowercase slug; there is no community claim or creation check.

Backend `POST /api/core/post` requires `protocol_version=1` or returns `426 upgrade_required`. Send `community` in the JSON body — the legacy `topic` key is no longer read and a body carrying only `topic` is rejected as a missing community.

Every post the backend serves now carries `community` and `root_community`. The old `topic` and `root_topic` response keys are gone; a client still reading them sees null and renders an empty community. `GET /api/get_posts` takes `community=` as its query param and returns `topic_retired` if you send `topic=`.

Canonical signing for `MsgPost` appends uvarint `1` at tag 106 after the repeated media tags.

During the temporary bridge only, the old `topic` request field is copied to `community`, protocol-0 signatures omit tag 106, and responses add `topic` / `root_topic` without removing the community fields. Do not reproduce those exceptions in migrated code.

Threads whose root was created before v1.39 have no chain metadata, so the chain cannot resolve a root for a new reply and rejects it with `legacy_thread_read_only` (HTTP 400). This is permanent and applies to protocol-1 replies too, not just bridge traffic: those threads stay readable and votable but can never receive another reply. Surface the copy as read-only rather than as a failed send, and disable the reply composer once a thread returns this code.

## Membership

`MsgJoinCommunity` payload is only `community` at tag 100. There is no target field. `MsgBlockCommunity` keeps `target=100` and `community=101`.

Joining stores `LIVE_DEFAULT` (mode 0). Pinning a team is `PINNED` (mode 1) plus `pinned_team_id`. Raw is mode 2 with no team. Pending operation key is `(message_type, community_or_empty, team_id_or_0, target_or_empty)`.

`GET /api/communities?joined_by={address}` lists joined communities. `/api/get_user_followed` is followed users only.

## Curator teams

A community is the slug itself and has no owner, founder, title, or description. Zero live teams means Uncurated; one or more live teams means Curated. `GET /api/communities` returns `community`, `curated`, `live_team_count`, `post_count`, and a nullable `default_team` summary. `GET /api/communities/:slug` must return 200 for every valid slug, including an empty uncurated slug.

Use `MsgCreateCurationTeam` for team creation: `community=100`, `name=101`, and `description=102`. Put moderation guidance in `description` — there is no separate policy field. The signing user becomes the leader and only initial member. Never send an initial curator list.

Team identity is `(community, team_id)`. A team may have ten accepted members total. Only the leader may edit the profile, invite or revoke invites, remove members, transfer leadership, toggle subscriber-only posting, or delete the team. Invitees sign accept or decline; an invitation alone never grants membership. Accepted curators may hide posts, hide users, and lock threads for their team lens.

Display `subscriber_count`, never `supporter_count`. It counts only actively paid users who explicitly pin that team. A free user can still select a team lens but does not increment the count. The standard node default is the live team with the highest count, then the oldest team and lowest ID.

## Reads

Lens query param: `effective`, `default`, `team`, or `raw`. `team` requires `team_id`. `scope=current` is the unified feed and includes both protocol-1 posts and readable protocol-0 history. `scope=legacy` is the protocol-0-only archive; it does not make old posts disappear from `current`.

Key every feed, post, thread, search, and local restoration cache by `(community, scope, lens, team_id, viewer)`. Changing a preference or team state invalidates all affected reads. A deleted pinned team resolves immediately to `LIVE_DEFAULT`; show one notice and do not keep presenting it as selected.

Authenticated feed, search, bootstrap, and profile-content reads send `address` plus `pubkey`, `signature`, `timestamp`, and `envelope_nonce` as query fields. Sign the UTF-8 payload `get_posts:<derived_address>:<timestamp>:<envelope_nonce>`; thread/comment reads sign `get_comments:<derived_address>:<timestamp>:<envelope_nonce>`. The derived address must equal `address`. If these proof fields are absent, the backend treats the request as a guest even when `address` is present. Invalid or partial proof returns 401.

The bridge temporarily honors an unsigned valid `address` on ordinary feed and thread reads when `X-Mirage-Visitor` is absent. That value is spoofable and provides personalization only; it never establishes identity or authorizes a write, reward, curator, or admin action. Migrated clients must not depend on it.

Curator invitation, moderation, hidden-user, and hidden-post reads use the same four proof fields with `viewer` as the claimed address and sign `curator_read:<derived_address>:<timestamp>:<envelope_nonce>`. Missing or invalid proof returns 401; a valid signer who is not an eligible curator returns 403. Read proofs do not consume transaction nonces.

Filter order: node policy and personal blocks, then stored/raw/pinned/default lens, then team hidden post, team hidden author (follow bypasses only this), subscriber-only against `was_subscriber_at_creation`, then thread lock.

A thread lock is a read filter, not a write gate: the chain and the relay both accept a reply to a locked thread, and it stays visible on `raw`. The root of `GET /api/get_comments` carries `thread_locked` for the requested lens — suppress the reply composer when it is true rather than letting the user spend quota on a comment that lens will hide. `comments` on that root counts only what the response returns, so never recompute it from an unfiltered source.

## Content tags

A post's `tag` as served is already the effective one. For `effective`, `default`, and `team`, precedence is the lens team's per-post override, then the community tag, then the author's own tag. An override of `""` is a curator asserting the post carries no tag, which is distinct from having no override. For `raw`, team per-post overrides never apply: precedence is the community tag, then the author's tag. Do not re-derive the result. The community tag comes from the community's default team and deliberately applies on `raw`.

`MsgSetCurationTag` sets the community tag and is leader-only: `community=100`, `team_id=101`, `tag=102`. `MsgSetCurationPostTag` sets a per-post override and is open to any accepted curator: `community=100`, `team_id=101`, `target=102`, `tag=103`, `clear=104`. Send `clear=true` to drop an override entirely; sending `tag=""` with `clear=false` records "no tag" instead. Both accept only the existing content-safety vocabulary (`""`, `sensitive`, `adult`, `gore`, `violence`, `death`), and a post carries one tag. The curator moderation endpoint returns the current override as `post_tag`.

## Subscriptions

`MsgSubscribe` field 102 is `period_count` in `[1,12]`. Self-purchase, gift, and renewal share that field. Relays are zero-fee when the owner's tier has `max_daily_relays > 0` (paid subscriber or appointed admin). Daily quota is that tier field; `subscriber_daily_relay_limit` is the subscriber-tier alias. Bootstrap `daily_quota` is null for free users or `{epoch, used, limit, remaining, reset_at}` for a relay-quota user. Quota error is `subscriber_daily_limit_reached` with the same accounting fields.

Bootstrap `renewal_warning` is null or `{expiry, next_attempt, last_attempt_epoch, warning_sent}`. Surface the expiry warning and link to subscription management. Do not send relay-reserve fields. Do not treat `level>=1` as paid. Use `effective_paid`.

During the bridge, a subscription signature that omits tag 102 buys one period. A cached level-10 purchase is accepted only as a one-period ordinary subscriber purchase at the subscriber price; it does not restore Agent status. New code must send level 1 and an explicit `period_count`.

## Creator claims

`POST /api/core/claim_creator_rewards` takes unique, strictly increasing `epoch_ids`. The maximum batch is the `max_creator_claim_epochs` returned by `GET /api/creator/earnings`; never hardcode 30.

`GET /api/creator/earnings?creator=` accepts `limit` from 1 to 100, `cursor`, `claimable_only=true|false`, and `sort=oldest|newest`. Claim screens use `claimable_only=true&sort=oldest`. Follow `next_cursor` while `has_more` is true so claimed rows or the first page cannot hide older claimable earnings. Amounts are decimal strings.

Each earnings item includes a first page of attributed posts plus `posts_next_cursor` and `posts_has_more`. Continue with `GET /api/creator/earnings/:epoch_id/targets?creator=&limit=&cursor=` until `has_more` is false; do not treat the embedded page as the complete attribution.

Show claimable, claimed, and expired epochs separately and explain expiry. A successful synchronous broadcast is not financial confirmation: wait for successful DeliverTx and then for every submitted item to carry a non-null `claimed_height`. Only then refresh earnings and account balance or show success. On rejection or timeout, keep the epochs selectable for retry.

## Target retired APIs (410)

After the bridge is removed, `/api/get_topics`, `/api/search_topics`, `/api/core/follow_topic`, `/api/core/unfollow_topic`, `/api/core/block_topic`, and `/api/core/unblock_topic` return 410. They are temporarily restored only for the currently published mobile release. `/api/core/create_community`, community metadata/founder/transfer routes, Agent and annotate writes, reward claims, referral writes, quest writes, and invite validation remain 410 throughout the bridge. Agent, reward, invite, and referral summary reads may return typed empty or disabled models temporarily so the old UI does not crash; that is not feature support.

## Renamed response fields and error codes

Alongside `community` / `root_community` on posts: `/api/get_chain_config` returns `max_community_size` and `min_community_size`; `/api/get_preferences` returns `communities` as `[{community, weight}]`; search returns `communities` and `has_more_communities`, and the `#` prefix yields `search_type` `community`; `/api/get_stats` returns `most_active_communities`; the bootstrap `view` param takes `community:<slug>` instead of `topic:<slug>`.

Error codes renamed: `topic_too_short` to `community_too_short`, `topic_too_long` to `community_too_long`, `topic_invalid_format` to `community_invalid_format`, `topic_too_many_wildcards` to `community_too_many_wildcards`, `topic_required` to `post_community_required`, `comment_must_not_include_topic` to `comment_must_not_include_community`, `topic_already_blocked` to `community_already_blocked`, and `topic_already_followed` to `community_already_joined`. Every `*_agent_*` code was deleted outright rather than renamed — the messages that produced them are rejected by the chain, so the codes were unreachable.

## Profile / bootstrap JSON

Expect `effective_paid`, `joined_communities`, `community_preferences`, `daily_quota` or null, `renewal_warning` or null. Do not expect `enabled_agents`, `followed_topics`, or relay-reserve fields.

## Cache invalidation

After join/leave/preference/team/claim settlement, invalidate community detail, community posts, teams, the affected thread, home, profile, search, inbox, and creator caches.
